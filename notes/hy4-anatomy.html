混元4 preview 模型结构分析Hunyuan 4 preview Model Architecture Analysis

分析对象是腾讯混元团队的 Hy4 preview,模型卡 tencent/Hy4-preview,架构名 HYV4ForCausalLM,Apache-2.0。用的还是两个元数据文件:config.json 与 model.safetensors.index.json。 The subject is Hy4 preview from the Tencent Hunyuan team — model card tencent/Hy4-preview, architecture HYV4ForCausalLM, Apache-2.0. As before, everything here comes from two metadata files: config.json and model.safetensors.index.json.

半个月前我用同样的方法拆过 Hy3。这一代不是把参数堆大那么简单 —— 注意力整个换了架构,残差也换了。所以这篇除了算账,更多篇幅在看它改了什么。 Two weeks ago I took Hy3 apart the same way. This generation is not just a bigger pile of parameters — the attention architecture was swapped outright, and so was the residual path. So beyond counting, most of this note is about what changed.

一、这次少了一样东西1 · Something is missing this time

拆 Hy3 时,index.json 的 metadata.total_size 给了权威的字节数,我拿它和逐项推算对了账。Hy4 的 index 里 metadata 是空的,没有这个数;张量条目也只有 2006 条(Hy3 有 47138),因为 256 个专家被融合成了一个张量。 With Hy3, index.json carried an authoritative byte count in metadata.total_size, and I reconciled my term-by-term estimate against it. Hy4 ships an empty metadata block — no such number. The index also lists only 2,006 tensors against Hy3's 47,138, because the 256 experts are fused into a single tensor per layer.

所以这次换了个更硬的办法:直接读 safetensors 的文件头。这个格式开头 8 字节是小端 u64 的头长度,紧跟一段 JSON,里面写明每个张量的 dtype 与 shape。用 HTTP Range 只取每个分片的前几十 KB 就够了 —— 131 个分片全部读到,没有失败,于是拿到的不是估算而是逐个张量的真实形状。 So this time I used something firmer: read the safetensors headers directly. The format opens with an 8-byte little-endian u64 header length, followed by JSON naming every tensor's dtype and shape. An HTTP Range request for the first few tens of KB of each shard is enough — all 131 shards came back, none failed. What that yields is not an estimate but the real shape of every single tensor. 

# safetensors header: 8-byte length + JSON
req = Request(url, headers={'Range': 'bytes=0-131071'})
d   = urlopen(req).read()
n   = struct.unpack('<Q', d[:8])[0]
hdr = json.loads(d[8:8+n])
# {"model.layers.1.mlp.experts.gate_up_proj":
#     {"dtype":"BF16","shape":[256,4096,6144], ...}}

三、注意力整个换掉:GQA → Gated DSA3 · Attention swapped outright: GQA → Gated DSA

这是 Hy4 最大的结构变化。Hy3 用的是老实的 GQA(64 个 Q 头 / 8 个 KV 头 / head_dim 128)。Hy4 的 config 里写着 use_mla: true、use_dsa: true、gated_mla: true,权重里对应的是一整套 MLA 低秩压缩结构: This is Hy4's biggest structural change. Hy3 used plain GQA — 64 query heads, 8 KV heads, head_dim 128. Hy4's config sets use_mla: true, use_dsa: true and gated_mla: true, and the weights carry a full low-rank MLA stack to match:

关键在第三格:真正进 KV cache 的只有 512 + 64 = 576 个数,而不是展开后的 64 头 × 256 维。kv_b_proj 是在读缓存时才把它还原成各头的 K/V。这就是 MLA 省显存的全部秘密,也是第七节那条曲线的来源。 The third box is the point: only 512 + 64 = 576 numbers per token per layer ever enter the KV cache, not the expanded 64 heads × 256 dims. kv_b_proj reconstitutes the per-head K/V at read time. That is the whole of MLA's memory saving, and the source of the curve in section 7.

还有两处小东西值得点名。linear_gate.weight 的形状是 (16384, 6144) —— 和 o_proj 一样大,单层就 100.7 M,全模型 7.9 B。这是 gated_mla 的代价,不算小。另外每层有一个 learnable_sink_param(64 个数,对应 64 个头),对应 learnable_sink: true —— attention sink 从固定位置变成了可学习的标量。 Two smaller things deserve naming. linear_gate.weight has shape (16384, 6144) — exactly as large as o_proj — 100.7 M per layer, 7.9 B across the model. That is the price of gated_mla, and it is not small. Each layer also carries a learnable_sink_param of 64 values, one per head, matching learnable_sink: true: the attention sink went from a fixed position to a learned scalar.

四、IndexCache:78 层只养 21 套索引4 · IndexCache: 78 layers, only 21 indexers

DSA 的稀疏是靠一个 indexer 先给每个 query 挑出 top-2048 个 key,再只在这些位置上算注意力(index_topk: 2048,index_n_heads: 32,index_head_dim: 128)。我本来以为 78 层各有一套,结果只有 21 层带 indexer 张量。 DSA gets its sparsity from an indexer that first picks the top-2048 keys for each query, after which attention runs only over those positions (index_topk: 2048, index_n_heads: 32, index_head_dim: 128). I assumed all 78 layers would carry one. In fact only 21 layers hold indexer tensors.

对上 config 才发现原因:indexer_types 这个数组里,值是 full 和 shared 交替的,而带 indexer 权重的层号恰好就是所有 full 的位置。模型卡把这个机制叫 IndexCache —— 跨层复用稀疏索引:一层算出来的 top-k 选择,后面几层直接拿来用,不再重算。 Cross-referencing the config explains it: the indexer_types array alternates between full and shared, and the layers carrying indexer weights are exactly the full positions. The card calls this IndexCache — reusing the sparse index across layers: the top-k selection computed by one layer is handed to the next few instead of being recomputed.

动图 3:78 层的 indexer 分布(鼠标划过看细节)Figure 3 · Indexer distribution across 78 layers (hover for detail)
full — 自己算索引(21 层)full — computes its own index (21 layers) shared — 复用上游索引(57 层)shared — reuses an upstream index (57 layers) dense FFN(仅第 0 层)dense FFN (layer 0 only)
规律很整齐:第 0、1 层各自算,之后每 4 层一个 full(5、9、13 … 77)。也就是说索引的计算量只有朴素做法的 27%,而 indexer 权重本身也只存 21 份。这是个纯粹的工程优化 —— 相邻层选中的 token 高度重合,那就没必要每层重挑一遍。 The pattern is tidy: layers 0 and 1 each compute their own, then one full layer every four (5, 9, 13 … 77). Index compute therefore drops to 27% of the naive layout, and only 21 copies of the indexer weights are stored. This is pure engineering — adjacent layers select heavily overlapping tokens, so there is no reason to re-pick every layer.

五、iHC:残差从一条变成四条5 · iHC: one residual path becomes four

权重里还有一组在 Hy3 完全不存在的张量:每层两组 hc_pre.{hc_base, hc_fn, hc_scale},外加一个全局的 model.hc_head.*。对应 config 里的 enable_ihc: true、hc_mult: 4。 The weights also contain a family that simply does not exist in Hy3: two sets of hc_pre.{hc_base, hc_fn, hc_scale} per layer, plus a global model.hc_head.*. These match enable_ihc: true and hc_mult: 4 in the config.

模型卡称之为 iHC(identity Hyper-Connections),规格表里那行「Residual Streams: 4」就是它 —— 残差通路从一条拓宽成四条并行的流,层与层之间用学到的系数在这四条流之间做混合。hc_fn 的形状 (8, 24576) 正好是 2 × hc_mult × hidden = 8 × 24576,对得上。 The card names it iHC (identity Hyper-Connections); the spec table's "Residual Streams: 4" is this — the residual path widens from one stream to four parallel ones, with learned coefficients mixing between them from layer to layer. The shape of hc_fn, (8, 24576), is exactly 2 × hc_mult × hidden = 8 × 24576. It checks out.

成本极低:整个 iHC 加起来只有 0.03 B 参数,占总量 0.004%。这类改动的特点就是几乎不花参数,却动了信息在深度方向的流动方式。 It costs almost nothing: all of iHC comes to 0.03 B parameters, 0.004% of the model. That is characteristic of this class of change — it barely spends parameters, yet it alters how information flows through depth.

单专家参数翻倍是两个因素叠出来的:中间维从 1536 到 2048(1.33×),hidden 从 4096 到 6144(1.5×)。专家数只加了三分之一,但因为每个都更宽,单层 MoE 的参数量变成了 2.6 倍。激活的专家数没变,所以稀疏度反而从 14.5× 上升到 15.9×。 Per-expert parameters doubled from two compounding factors: intermediate size 1536 → 2048 (1.33×) and hidden 4096 → 6144 (1.5×). The expert count only grew by a third, but because each is wider, a single MoE layer got 2.6× heavier. The number of activated experts did not change, so sparsity actually rose from 14.5× to 15.9×.

七、上下文 ×4,每 token 的 KV 反而省了7 · 4× the context, and less KV per token

这是我觉得整份 config 里最漂亮的一处。Hy3 靠 GQA 把 KV 压到八分之一,每 token 每层仍要存 2 × 8 头 × 128 = 2048 个数。Hy4 换成 MLA 之后,进缓存的只有压缩后的 kv_lora_rank + qk_rope_head_dim = 512 + 64 = 576 个数。 This is the prettiest thing in the whole config. Hy3's GQA cut KV to an eighth, but still stored 2 × 8 heads × 128 = 2048 numbers per token per layer. With MLA, what enters the cache is just the compressed kv_lora_rank + qk_rope_head_dim = 512 + 64 = 576.

Hy3 在 256K 时要 80 GiB;Hy4 在 1M 时是 87.8 GiB。上下文长了 4 倍,KV 只多了 10%。代价是 kv_b_proj 那步还原计算 —— 用一点算力换了四倍的窗口。另外 21 层 indexer 还各要一份自己的 key 缓存(index_head_dim 128),按结构推算约 5.2 KiB/token,1M 时再加约 5.2 GiB。 Hy3 needs 80 GiB at 256K; Hy4 needs 87.8 GiB at 1M. Four times the context for 10% more KV. The price is the kv_b_proj reconstruction step — a little compute traded for a 4× window. Separately, the 21 indexer layers each need their own key cache (index_head_dim 128), which the structure implies is about 5.2 KiB/token, adding roughly 5.2 GiB at 1M.

八、BF16 装不下,所以官方直接发 FP88 · BF16 doesn't fit, so the FP8 repo is the real one

权重 BF16 是 1452.8 GiB,是 Hy3 的 2.6 倍。这个体积意味着:8 卡无论 H100 还是 H20-3e,BF16 都放不进去,连权重都装不下,更别说 KV。 BF16 weights come to 1452.8 GiB, 2.6× Hy3. At that size, eight GPUs cannot hold them on either H100 or H20-3e — not the weights alone, let alone any KV.

所以官方仓库里还有一个 tencent/Hy4-preview-FP8,而且部署脚本里 --tensor-parallel-size 8 后面跟的正是 FP8 那个仓库。我把 FP8 版的 130 个分片头部也读了一遍:专家权重是 F8_E4M3,配一组 U8 的 block scale,实测 757.9 GiB,压到 BF16 的 52.2%(不是 50%,因为 scale 和没量化的部分还占 43 GB)。 Which is why the org also publishes tencent/Hy4-preview-FP8, and why the deployment recipe points --tensor-parallel-size 8 at that repo rather than this one. I read all 130 FP8 shard headers too: expert weights are F8_E4M3 with a set of U8 block scales, measuring 757.9 GiB — 52.2% of BF16, not 50%, because the scales and the un-quantised parts still account for 43 GB.

读下来会发现两代的取舍很不一样。Hy3 是把成熟方案(GQA + DeepSeek 式路由)做扎实;Hy4 则在注意力和残差两条主干上同时换了新东西,换来的是四倍上下文和更省的 KV,代价是权重体积翻了 2.6 倍、必须靠 FP8 才装得下。 Read together, the two generations made very different bets. 十、要点10 · Takeaways

01
没有 total_size 就去读文件头No total_size? Read the headers

Hy4 的 index 把 metadata 留空了。safetensors 开头 8 字节是头长度、紧跟 JSON,用 HTTP Range 取每个分片前几十 KB 就能拿到逐张量的真实 shape,比 total_size 还硬。Hy4 left metadata empty. Safetensors opens with an 8-byte length then JSON, so a Range request for the first few tens of KB of each shard yields the true shape of every tensor — firmer evidence than total_size ever was.

02
MLA 让上下文和显存脱钩MLA decouples context from memory

进缓存的只有压缩后的 512+64,而不是展开的 64 头 × 256 维。于是上下文从 256K 涨到 1M,KV 总量只从 80 GiB 变成 87.8 GiB。用 kv_b_proj 的还原计算换了四倍窗口。Only the compressed 512+64 enters the cache, not the expanded 64 heads × 256 dims. Context grew from 256K to 1M while total KV went from 80 GiB to just 87.8 GiB — a 4× window bought with the kv_b_proj reconstruction.

03
稀疏索引也可以跨层复用Sparse indices can be reused across layers

78 层里只有 21 层真的持有 indexer,其余复用上游的选择结果。相邻层选中的 token 高度重合,那就没必要每层重挑 —— 索引计算量直接降到 27%。Only 21 of 78 layers actually hold an indexer; the rest reuse an upstream selection. Adjacent layers pick heavily overlapping tokens, so re-picking every layer is wasted work — index compute falls to 27%.

04
有些改动几乎不花参数Some changes cost almost no parameters

iHC 把残差拓宽成 4 条流,总共只用了 0.03 B,占比 0.004%。它改的不是容量,是信息在深度方向的流动方式 —— 这类改动在参数表上完全看不出来。iHC widens the residual into four streams for a total of 0.03 B, 0.004% of the model. It changes not capacity but how information moves through depth — the kind of change a parameter table cannot show you.

05
gated 不是免费的Gating is not free

linear_gate 和 o_proj 一样大,单层 100.7 M,全模型 7.9 B。比整个 iHC 大两个数量级。给注意力加门控,账要算在这里。linear_gate is the same size as o_proj: 100.7 M per layer, 7.9 B in total — two orders of magnitude more than all of iHC. If you gate attention, this is where the bill lands.

06
量化从可选项变成前提Quantisation stopped being optional

1452.8 GiB 意味着 8 卡在 BF16 下连权重都装不下,H20-3e 也不行。官方直接发 FP8 仓库并让部署脚本指向它 —— 到这个尺寸,量化已经不是优化而是能不能跑的问题。1452.8 GiB means eight GPUs cannot hold the weights in BF16, H20-3e included. The org publishes an FP8 repo and points the recipe at it — at this size, quantisation is no longer an optimisation but the difference between running and not.
