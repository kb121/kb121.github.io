混元4 preview 模型结构分析Hunyuan 4 preview Model Architecture Analysis

分析对象是腾讯混元团队的 Hy4 preview,模型卡 tencent/Hy4-preview, 架构名 HYV4ForCausalLM,Apache-2.0。用的还是两个元数据文件: config.json 与 model.safetensors.index.json。

半个月前我用同样的方法拆过 Hy3。这一代不是把参数堆大那么简单 —— 注意力整个换了架构,残差也换了。所以这篇除了算账,更多篇幅在看它改了什么。

779.96 B实测总参数(含 MTP)
49.03 B每 token 激活,稀疏 15.9×
87.8 KiB每 token KV,比 Hy3 省 3.65×
21 / 78真正持有 indexer 的层
1452.8 GiBBF16 权重,8 卡放不下

一、这次少了一样东西

拆 Hy3 时,index.json 的 metadata.total_size 给了权威的字节数, 我拿它和逐项推算对了账。Hy4 的 index 里 metadata 是空的,没有这个数; 张量条目也只有 2006 条(Hy3 有 47138),因为 256 个专家被融合成了一个张量。

所以这次换了个更硬的办法:直接读 safetensors 的文件头。 这个格式开头 8 字节是小端 u64 的头长度,紧跟一段 JSON,里面写明每个张量的 dtype 与 shape。 用 HTTP Range 只取每个分片的前几十 KB 就够了 —— 131 个分片全部读到,没有失败, 于是拿到的不是估算而是逐个张量的真实形状。 

# safetensors 头部:8 字节长度 + JSON
req = Request(url, headers={'Range': 'bytes=0-131071'})
d   = urlopen(req).read()
n   = struct.unpack('<Q', d[:8])[0]
hdr = json.loads(d[8:8+n])
# {"model.layers.1.mlp.experts.gate_up_proj":
#     {"dtype":"BF16","shape":[256,4096,6144], ...}}

二、总账:770 B 主干 + 10 B MTP

把 2006 个张量按 dtype 逐个累加:

动图 1:779.96 B 参数都在哪

和 Hy3 一样,MTP 是单独计的:规格表的 770 B 不含它,磁盘上实际躺着 779.96 B。 不同的是这次它被放进 model.mtp_layers.0.*,而不是 Hy3 那种伪装成第 80 层的写法 —— 命名干净了。 它也从 3.75 B 涨到了 10.05 B。

三、注意力整个换掉:GQA → Gated DSA

这是 Hy4 最大的结构变化。Hy3 用的是老实的 GQA(64 个 Q 头 / 8 个 KV 头 / head_dim 128)。 Hy4 的 config 里写着 use_mla: true、use_dsa: true、gated_mla: true, 权重里对应的是一整套 MLA 低秩压缩结构:

关键在第三格:真正进 KV cache 的只有 512 + 64 = 576 个数, 而不是展开后的 64 头 × 256 维。kv_b_proj 是在读缓存时才把它还原成各头的 K/V。 这就是 MLA 省显存的全部秘密,也是第七节那条曲线的来源。

还有两处小东西值得点名。linear_gate.weight 的形状是 (16384, 6144) —— 和 o_proj 一样大,单层就 100.7 M,全模型 7.9 B。这是 gated_mla 的代价, 不算小。另外每层有一个 learnable_sink_param(64 个数,对应 64 个头), 对应 learnable_sink: true —— attention sink 从固定位置变成了可学习的标量。

四、IndexCache:78 层只养 21 套索引

DSA 的稀疏是靠一个 indexer 先给每个 query 挑出 top-2048 个 key,再只在这些位置上算注意力 (index_topk: 2048,index_n_heads: 32,index_head_dim: 128)。 我本来以为 78 层各有一套,结果只有 21 层带 indexer 张量。

对上 config 才发现原因:indexer_types 这个数组里,值是 full 和 shared 交替的, 而带 indexer 权重的层号恰好就是所有 full 的位置。模型卡把这个机制叫 IndexCache —— 跨层复用稀疏索引:一层算出来的 top-k 选择,后面几层直接拿来用,不再重算。

动图 3:78 层的 indexer 分布(鼠标划过看细节)
full — 自己算索引(21 层) shared — 复用上游索引(57 层) dense FFN(仅第 0 层)
规律很整齐:第 0、1 层各自算,之后每 4 层一个 full(5、9、13 … 77)。 也就是说索引的计算量只有朴素做法的 27%,而 indexer 权重本身也只存 21 份。 这是个纯粹的工程优化 —— 相邻层选中的 token 高度重合,那就没必要每层重挑一遍。

五、iHC:残差从一条变成四条

权重里还有一组在 Hy3 完全不存在的张量:每层两组 hc_pre.{hc_base, hc_fn, hc_scale}, 外加一个全局的 model.hc_head.*。对应 config 里的 enable_ihc: true、hc_mult: 4。

模型卡称之为 iHC(identity Hyper-Connections),规格表里那行 「Residual Streams: 4」就是它 —— 残差通路从一条拓宽成四条并行的流,层与层之间用学到的系数在这四条流之间做混合。 hc_fn 的形状 (8, 24576) 正好是 2 × hc_mult × hidden = 8 × 24576,对得上。

成本极低:整个 iHC 加起来只有 0.03 B 参数,占总量 0.004%。 这类改动的特点就是几乎不花参数,却动了信息在深度方向的流动方式。

六、MoE:专家更多,也更宽

单专家参数翻倍是两个因素叠出来的:中间维从 1536 到 2048(1.33×),hidden 从 4096 到 6144(1.5×)。 专家数只加了三分之一,但因为每个都更宽,单层 MoE 的参数量变成了 2.6 倍。 激活的专家数没变,所以稀疏度反而从 14.5× 上升到 15.9×。

七、上下文 ×4,每 token 的 KV 反而省了

这是我觉得整份 config 里最漂亮的一处。Hy3 靠 GQA 把 KV 压到八分之一, 每 token 每层仍要存 2 × 8 头 × 128 = 2048 个数。 Hy4 换成 MLA 之后,进缓存的只有压缩后的 kv_lora_rank + qk_rope_head_dim = 512 + 64 = 576 个数。

动图 4:KV cache 随上下文增长(同一张图上比两代)
上下文Hy3 · GQA(320 KiB/token)Hy4 · MLA(87.8 KiB/token)
Hy3 在 256K 时要 80 GiB;Hy4 在 1M 时是 87.8 GiB。 上下文长了 4 倍,KV 只多了 10%。 代价是 kv_b_proj 那步还原计算 —— 用一点算力换了四倍的窗口。 另外 21 层 indexer 还各要一份自己的 key 缓存(index_head_dim 128), 按结构推算约 5.2 KiB/token,1M 时再加约 5.2 GiB。

八、BF16 装不下,所以官方直接发 FP8

权重 BF16 是 1452.8 GiB,是 Hy3 的 2.6 倍。这个体积意味着: 8 卡无论 H100 还是 H20-3e,BF16 都放不进去,连权重都装不下,更别说 KV。

所以官方仓库里还有一个 tencent/Hy4-preview-FP8, 而且部署脚本里 --tensor-parallel-size 8 后面跟的正是 FP8 那个仓库。我把 FP8 版的 130 个分片头部也读了一遍: 专家权重是 F8_E4M3,配一组 U8 的 block scale,实测 757.9 GiB, 压到 BF16 的 52.2%(不是 50%,因为 scale 和没量化的部分还占 43 GB)。

读下来会发现两代的取舍很不一样。Hy3 是把成熟方案(GQA + DeepSeek 式路由)做扎实; Hy4 则在注意力和残差两条主干上同时换了新东西, 换来的是四倍上下文和更省的 KV,代价是权重体积翻了 2.6 倍、必须靠 FP8 才装得下。

十、要点

01
没有 total_size 就去读文件头

Hy4 的 index 把 metadata 留空了。safetensors 开头 8 字节是头长度、紧跟 JSON,用 HTTP Range 取每个分片前几十 KB 就能拿到逐张量的真实 shape,比 total_size 还硬。

02
MLA 让上下文和显存脱钩

进缓存的只有压缩后的 512+64,而不是展开的 64 头 × 256 维。于是上下文从 256K 涨到 1M,KV 总量只从 80 GiB 变成 87.8 GiB。用 kv_b_proj 的还原计算换了四倍窗口。

03
稀疏索引也可以跨层复用

78 层里只有 21 层真的持有 indexer,其余复用上游的选择结果。相邻层选中的 token 高度重合,那就没必要每层重挑 —— 索引计算量直接降到 27%。

04
有些改动几乎不花参数

iHC 把残差拓宽成 4 条流,总共只用了 0.03 B,占比 0.004%。它改的不是容量,是信息在深度方向的流动方式 —— 这类改动在参数表上完全看不出来。

05
gated 不是免费的

linear_gate 和 o_proj 一样大,单层 100.7 M,全模型 7.9 B。比整个 iHC 大两个数量级。给注意力加门控,账要算在这里。

06
量化从可选项变成前提

1452.8 GiB 意味着 8 卡在 BF16 下连权重都装不下,H20-3e 也不行。官方直接发 FP8 仓库并让部署脚本指向它 —— 到这个尺寸,量化已经不是优化而是能不能跑的问题。

结构与参数量仅由 config.json 与 model.safetensors.index.json 推导, 字节数由 HTTP Range 读取 131 个 safetensors 分片头部的真实 shape 累加得到,未下载权重本体; 推算完成后才与模型卡规格表核对。indexer 的额外 key 缓存为按结构推断,非官方数字。 显存部分只算权重与 KV,未计激活与框架 workspace,属乐观上界;GPU 容量按标称值计。
