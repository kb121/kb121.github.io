从一份 config 读懂并行切分:TP=4 / PP=4 / EP=4

并行策略这件事,光看名词很容易糊涂:TP 到底切的是什么?切 head_dim 还是切 head 数?EP 和 TP 是不是一回事? 这篇笔记不讲抽象定义,直接拿一份真实的 tencent/Hy3 config.json 当底稿,把 TP=4、PP=4、EP=4 落到每一个张量的 shape 上,配动图看清数据怎么流。最后在 Extra 里补齐 DP / SP / CP 等其余维度。

一句话总览: 三种并行切的是三个完全正交的维度——TP 切"宽度"(一层之内的 head 数 / FFN 中间维),PP 切"深度"(80 层分成 4 段),EP 切"专家数"(192 个专家分给 4 组)。而 head_dim=128 是唯一那个谁都不许切的维度。

0 · 先把这份 config 读明白

只挑和并行相关的字段,其余(token id、rope、norm)先略过:

{
  "hidden_size": 4096,            // 残差流宽度 d_model
  "head_dim": 128,                // ← 注意:显式给出,不是 hidden/heads
  "num_attention_heads": 64,      // Q head 数
  "num_key_value_heads": 8,       // KV head 数 → GQA,8 个 Q 共享 1 个 KV
  "num_hidden_layers": 80,        // 层数 → PP 切这里
  "intermediate_size": 13312,     // dense FFN 中间维
  "first_k_dense_replace": 1,     // 第 0 层是 dense FFN,第 1~79 层是 MoE
  "num_experts": 192,             // 路由专家数 → EP 切这里
  "num_experts_per_tok": 8,       // top-k:每 token 选 8 个专家
  "num_shared_experts": 1,        // 共享专家,每 token 必过
  "moe_intermediate_size": 1536,  // 单个专家的中间维
  "vocab_size": 120832,
  "max_position_embeddings": 262144,
  "num_nextn_predict_layers": 1,  // MTP(多 token 预测)层
  "dtype": "bfloat16"
}

由这些字段先把规模算出来,后面所有切分都围绕它转:

单层 attn = 4096×8192 + 2×(4096×1024) + 8192×4096 = 75.5M
单个专家 = 3 × 4096 × 1536 = 18.87M  |  单个 MoE 层 = 192 个专家 + 1 共享 + router = 3.64B
总参数 ≈ 80×75.5M + 163.6M + 79×3.64B + 2×(120832×4096) ≈ 295B
每 token 激活 ≈ 6.0B(attn) + 79×(8+1)×18.87M + emb/head ≈ 20.2B  (6.8%)
这是一个 ~295B 总参 / ~20B 激活的稀疏 MoE。 295B 的 bf16 权重 = 590 GB,单卡绝无可能;而 20B 的激活量又意味着算力需求远小于显存需求。这正是"必须并行、且要用 EP 而不是纯 TP"的根本原因。

1 · 第一个陷阱:head_dim ≠ hidden_size / num_heads

绝大多数人读 config 会下意识地算 4096 / 64 = 64,认为 head_dim=64。但这份 config 显式写了 head_dim: 128。两者对不上:

为什么这个细节对并行很关键? 因为切分的分母是 num_heads,而张量的宽度是 num_heads × head_dim。如果你按 hidden_size/TP 去算 q_proj 的分片大小,会得到 1024,而正确答案是 8192/4 = 2048——差了整整一倍,shape 直接对不上。

2 · TP=4:切的是 head 的个数,不是 head_dim

这是本文最想讲清的一点。张量并行在 attention 上的切法是:把 64 个 head 发牌一样分给 4 张卡,每卡 16 个完整的 head。每个 head 内部的 head_dim=128 原封不动。

为什么 head_dim 切不得?

因为一个 head 内部是一条不可分割的规约链:QKT 要沿 head_dim 做点积,softmax 又要沿序列做归一化。若把 head_dim 切开,每算一个注意力分数都得跨卡 all-reduce:

✅ 按 head 切(TP 的做法)
Q[16h,128]×KT →softmax→×V

整条链全在本卡完成,16 个 head 各算各的。只在最后 o_proj 之后做一次 all-reduce 把 4 张卡的部分和加起来。通信 = 每层 1 次。

❌ 按 head_dim 切(没人这么干)
Q[64h,32]×KT ⇅ all-reduce→softmax

点积被劈成 4 段部分和,每个 token、每个 head 的每个分数都要跨卡求和才能进 softmax。通信量爆炸,而且 QK-norm(qk_norm: true)也要沿 head_dim 归一化,同样被劈开。

TP=4 下每个张量的真实 shape

张量完整 shapeTP=4 每卡切法
q_proj[4096, 64×128=8192][4096, 2048] · 16 heads列并行(切 head)
k_proj / v_proj[4096, 8×128=1024][4096, 256] · 2 kv heads列并行(切 kv head)
o_proj[8192, 4096][2048, 4096]行并行 + all-reduce
head_dim128128(不变)✖ 永不切分
dense FFN gate/up
(仅第 0 层)		[4096, 13312][4096, 3328]列并行
dense FFN down[13312, 4096][3328, 4096]行并行 + all-reduce
embedding / lm_head[120832, 4096][30208, 4096]词表并行
GQA 的自洽性检查: 64 个 Q head 配 8 个 KV head,组大小 = 8。TP=4 后每卡是 16 Q + 2 KV,组大小还是 16/2 = 8 ✅。这说明 TP 必须整除 num_key_value_heads——本模型 KV head 只有 8,所以 TP ∈ {1,2,4,8} 是干净的;TP=16 就会不够分,只能把 KV head 复制到多卡(浪费显存)或改用别的策略。MoE 大模型 TP 开不大,这是主因之一。

3 · PP=4:切的是"深度"

流水线并行不动任何一个张量的 shape,它只是把 80 层按顺序切成 4 段,每段 20 层放一张(组)卡上。注意 first_k_dense_replace: 1 让第 0 层是 dense FFN,其余 79 层才是 MoE:

PP 的代价不是通信,而是 bubble(气泡):stage 3 必须等 stage 0/1/2 都算完才能开工。解法是把 batch 拆成 micro-batch 流水起来:

本模型 PP 切分的隐藏坑:负载不均。 Stage 0 多背一个 embedding(120832×4096 ≈ 0.49B),Stage 3 多背 lm_head(又 0.49B)加上 num_nextn_predict_layers: 1 的 MTP 层。所以"每段 20 层"看似整齐,实际首尾两段更重。生产上常用不均匀切分(如 21/20/20/19)把首尾的额外负担摊平。

4 · EP=4:切的是"专家数"

MoE 层里 192 个专家总共 3.62B 参数,但每个 token 只激活 8 个。专家并行的思路是:与其把每个专家都切碎(TP),不如让每张卡各自拿着一整批完整的专家。 192 / 4 = 每卡 48 个完整专家。

EP 的优点

  • 专家权重完整不切,GEMM 形状规整(1536 不用再除以 4),kernel 效率高。
  • 显存线性下降:每卡只存 48 个专家。
  • 通信量 ∝ 激活的 token 数,与专家总数无关——192 个专家和 1920 个专家通信一样多。

EP 的代价

  • 两次 All-to-All(dispatch + combine),延迟敏感、对网络拓扑挑剔。
  • 负载不均:热门专家所在卡被打爆,其余卡空等(见 Extra 的 EPLB)。
  • 需要 capacity factor / 丢 token 策略,或做 padding 浪费算力。
共享专家怎么处理? num_shared_experts: 1 意味着有 1 个专家每个 token 都要过。它不参与 EP 切分(切了等于所有 token 都得跨卡),通常是在每张卡上按 TP 切分并复制一份——即每卡持有 1536/4 = 384 的中间维分片。这样它和 attention 一样走 all-reduce,不进 All-to-All。

5 · 三者合体:16 张卡怎么摆

TP=4, PP=4, EP=4 最常见的落法(也是 vLLM --tensor-parallel-size 4 --pipeline-parallel-size 4 --enable-expert-parallel 的语义)是:EP 复用 TP 那一组卡。世界大小 = TP × PP = 16 张卡,而不是 4×4×4=64。

EP 不是独立乘上去的一维。 vLLM 里 enable_expert_parallel 的注释写得很直白——"Use expert parallelism instead of tensor parallelism for MoE layers"。也就是说同一批卡:attention 层按 TP 切,MoE 层改按 EP 切,EP size = TP × DP。所以别把 4×4×4 当成 64 卡去规划机器。

一个 token 穿过一层时,通信是这样发生的:

① attn
TP 组内
各算 16 个 head → o_proj 后 all-reduce
② router
本地
sigmoid 打分,选 top-8 / 192
③ MoE
EP 组内
all-to-all 派发 → 专家计算 → all-to-all 收回
④ 跨层
PP 边界
每 20 层一次 P2P 送 hidden state

6 · 显存账:这样切之后每张卡装什么

按上面 16 卡布局,取中间一个 stage(20 个 MoE 层)算单卡权重:

attn:  20 层 × 75.5M / 4  =  0.38B
专家:  20 层 × 48 个 × 18.87M  =  18.1B  ← 绝对大头
共享专家 + router: 20 层 × (18.87M/4 + 0.79M)  ≈  0.11B
────────────────────────
单卡权重 ≈ 18.6B × 2 bytes(bf16) ≈ 34.7 GiB

再看 KV cache。num_key_value_heads=8 的 GQA 已经把它压得很小,但 max_position_embeddings=262144 依然吓人:

整模型每 token = 2(K,V) × 8 kv_head × 128 × 80 层 × 2 B = 320 KiB
单卡每 token = 320 KiB / TP4 / PP4 = 20 KiB
一条 262144 的满长序列 = 80 GiB(全局) / 5 GiB(单卡)
单卡 34.7 GiB 权重 + KV cache,在 80 GB 卡上还剩约 40 GiB 给 KV,也就是约 8 条满长上下文的并发。想再提高并发,要么继续压 KV(量化到 fp8 直接减半),要么调 gpu-memory-utilization 把余额榨出来——那部分我在 《vLLM 的 gpu-memory-utilization 到底管什么》 里拆过。K/V 一路堆到 80 GiB 的完整过程,则在 《Q / K / V 在 256K 对话窗口中的一生》 里逐步演示过。

7 · Extra:其余并行维度

TP / PP / EP 之外,实际系统里还叠着好几层并行。这里按"切什么"归类速览:

维度切什么通信在这个模型上的意义
DP
数据并行		 切 batch,模型整份复制 训练:梯度 all-reduce
推理:无		 295B 权重单份就 590 GB,朴素 DP 完全不可行,必须配 ZeRO/FSDP 分片。
Attention-DP
(DeepSeek 式)		 attention 部分按 请求 切,MoE 部分共用 EP MoE 前后 all-to-all 对本模型很划算:KV head 只有 8,TP 越大 KV 复制/碎片越严重;改用 attention-DP 让每个 DP rank 管自己的 KV,再共享 EP 专家池。vLLM 的 --data-parallel-size 就是这个。
SP
序列并行		 切 序列长度(Megatron-SP 切 norm/dropout 那段激活) all-gather + reduce-scatter TP 的免费搭档:把 LayerNorm 处那份没被 TP 切的激活也切开,省激活显存。
CP
上下文并行
(Ring / Ulysses)		 切 序列长度,含 attention 本身 Ring: P2P 传 KV
Ulysses: all-to-all		 max_position_embeddings=262144 ⇒ 长上下文训练绕不开 CP。细节见 《主流序列并行方案对比》。
ZeRO / FSDP 切 优化器状态 / 梯度 / 参数 参数 all-gather 训练必备:295B 用 AdamW 的优化器状态是权重的数倍,不切根本放不下。
EPLB
专家负载均衡		 不是并行,是 EP 的补丁 — 把热门专家复制到多张卡、冷门专家合并,拉平 all-to-all 的长尾。moe_router_enable_expert_bias: true 说明这个模型训练时就带了 bias 式均衡。
MTP
多 token 预测		 num_nextn_predict_layers: 1 — 额外一个预测头,推理时可做自投机解码。放在最后一个 PP stage,是 stage 3 负载偏重的原因之一。
