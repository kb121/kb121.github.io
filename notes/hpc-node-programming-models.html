一句话总览: 大纲里的六件事不是六座孤岛。SIMD 和同步是横切机制,在每一种模型里都会再出现一次;OpenMP / CUDA / OpenCL / SYCL 是同一套执行层次上的四个 API,差别主要在「谁写 kernel、数据怎么搬、能跑上哪家硬件」。先把名字对齐,再上机,才不会把 team、block、work-group 当成三件不同的东西。In one line: the six items are not six islands. SIMD and synchronisation are cross-cutting mechanisms that reappear inside every model; OpenMP, CUDA, OpenCL and SYCL are four APIs over the same execution hierarchy, differing mainly in who writes the kernel, how data moves, and whose hardware it runs on. Align the vocabulary before you sit down at the machine, and you will not mistake team, block and work-group for three different things.

0 · 课在哪一层0 · Which layer this course sits on

HPC 程序通常叠三层:进程间(MPI)→ 节点内线程/队(OpenMP、CUDA grid)→ 核内向量(SIMD / warp)。这门课停在后两层。一个节点上你真正要调度的,是「若干 CPU 核 + 零到多块加速器 + 它们之间那条又窄又贵的总线」。HPC programs usually stack three layers: between processes (MPI) → threads and teams within a node (OpenMP, CUDA grid) → vectors within a core (SIMD / warp). This course stops at the latter two. What you actually schedule on one node is some number of CPU cores, zero or more accelerators, and the narrow, expensive bus between them.

1 · 先把名字对齐1 · Aligning the vocabulary first

异构设备几乎都按同一套三级来切工作:大范围切成组,组内再切成工作项,工作项在硬件上往往还被捆成一小波锁步执行。对照关系可以当字典用 —— 课上换 API 时,先在这张表里找同一行。Heterogeneous devices almost all carve up work the same three ways: a broad range split into groups, groups split into work items, and work items bundled on the hardware into small lockstep waves. 2 · SIMD:核里面那条向量带2 · SIMD: the vector lane inside a core

SIMD(Single Instruction, Multiple Data)是一条指令同时喂给多个数据通道。CPU 上它长在每个核的向量寄存器里:AVX2 是 256-bit,AVX-512 是 512-bit(16 个 float),ARM 的 NEON 通常 128-bit,Fujitsu A64FX / 部分 ARM 则是长度可伸缩的 SVE。编译器自动向量化、#pragma omp simd、手写 intrinsic,是同一件事的三个控制旋钮,从「听天由命」到「我指定通道数」。SIMD (Single Instruction, Multiple Data) feeds one instruction to several data lanes at once. On CPUs it lives in each core's vector registers: AVX2 is 256-bit, AVX-512 is 512-bit (16 floats), ARM's NEON is typically 128-bit, and Fujitsu A64FX and some ARM parts use length-agnostic SVE. Compiler auto-vectorisation, #pragma omp simd and hand-written intrinsics are three control knobs on the same thing, running from "leave it to fate" to "I am naming the lane count".

上课时值得主动查的三件事:Three things worth checking during the lab:

  • 对齐与单位跨步。 aligned(A:64)、restrict / __restrict 告诉编译器没有别名。跨步不是 1 的访问会变成 gather/scatter,向量化收益很快被吃光。Alignment and unit stride. aligned(A:64) and restrict / __restrict tell the compiler there is no aliasing. Accesses with stride other than 1 turn into gather/scatter, and the vectorisation gain evaporates fast.
  • 报告,不要猜。 Intel -qopt-report=3、Clang -Rpass=loop-vectorize、NVIDIA -Minfo=vect。报告里写 vectorized 才算数。Read the report, do not guess. Intel -qopt-report=3, Clang -Rpass=loop-vectorize, NVIDIA -Minfo=vect. It only counts if the report says vectorized.
  • 和 GPU 的 SIMT 不要混名。 GPU warp 也是「一拍多数据」,但编程模型按线程写,硬件再把相邻线程捆成 warp。CPU SIMD 是你(或编译器)在指令级把循环切成向量;GPU SIMT 是硬件把标量线程锁步执行。发散(if 让 warp 里一半走 A、一半走 B)会把一拍拆成两拍串行。Do not confuse it with GPU SIMT. A GPU warp is also many data per cycle, but the programming model is written per thread and the hardware bundles neighbouring threads into a warp afterwards. CPU SIMD is you (or the compiler) slicing the loop into vectors at the instruction level; GPU SIMT is hardware running scalar threads in lockstep. Divergence — an if sending half the warp down A and half down B — splits one cycle into two serial ones.
#pragma omp simd aligned(A, B, C: 64)
for (int i = 0; i < N; ++i)
    C[i] = A[i] + B[i];   /* 编译器负责挑 AVX-512 / SVE 宽度 */#pragma omp simd aligned(A, B, C: 64)
for (int i = 0; i < N; ++i)
    C[i] = A[i] + B[i];   /* the compiler picks the AVX-512 / SVE width */

3 · 同步:每个边界一把锁3 · Synchronisation: a lock at every boundary

并行程序里「算得快」和「算得对」之间隔的就是同步。课把 synchronization 单列一项,是因为它不属于某一个 API,而是每个 API 都要你显式或隐式选一种。What separates "fast" from "correct" in a parallel program is synchronisation. The course lists it separately because it belongs to no single API — every API makes you choose one, explicitly or implicitly.

  • Barrier / 栅栏。 OpenMP 并行区末尾默认有一道隐式 barrier(nowait 才拿掉);CUDA 的 __syncthreads() 只在 block 内有效;warp 内用 __syncwarp。跨 block 的栅栏不是默认能力。Barriers. An OpenMP parallel region has an implicit barrier at the end (removed only by nowait); CUDA's __syncthreads() works only within a block, and __syncwarp within a warp. A barrier across blocks is not a default capability.
  • 互斥 vs 原子 vs 规约。 critical 是一把大锁;atomic 是一条硬件原子;reduction 才是 HPC 里该先伸手去拿的 —— 它把「每人一份私有累加器,最后再合」这个模式写进运行时,避免伪共享。Mutex vs atomic vs reduction. critical is one big lock; atomic is a single hardware atomic; reduction is what you should reach for first in HPC — it encodes "a private accumulator each, combined at the end" into the runtime and avoids false sharing.
  • 伪共享(false sharing)。 两个线程写同一 cache line(常见 64 B)里的不同字节,一致性协议仍当它们在抢。OpenMP 里给每个线程的累加器做 padding,或直接用 reduction,这个坑在 CPU 多核实验里几乎必现。False sharing. Two threads writing different bytes of the same cache line (commonly 64 B) still look like contention to the coherence protocol. Padding each thread's accumulator, or just using reduction, avoids it; the trap shows up in almost every multi-core CPU lab.
  • 内存序。 C++ / OpenMP 5.x / CUDA 原子都有 relaxed / acquire-release / seq_cst。计数器用 relaxed 通常够;发布指针给别的线程看,就要 acquire-release。默认 seq_cst 正确但贵,报告里值得写你选了哪一档。Memory ordering. C++, OpenMP 5.x and CUDA atomics all offer relaxed / acquire-release / seq_cst. Relaxed is usually enough for a counter; publishing a pointer for another thread to read needs acquire-release. The seq_cst default is correct but expensive, and it is worth stating in the report which one you picked.
  • 数据传输也是同步。 cudaMemcpy、OpenMP map、SYCL accessor 的依赖图,本质都是「这边写完,那边才能读」。把 H2D/D2H 算进或不算进计时,会让同一段 kernel 的「加速比」差出一个数量级。Data transfer is synchronisation too. cudaMemcpy, OpenMP map and SYCL's accessor dependency graph all mean the same thing: this side finishes writing before that side can read. Counting H2D/D2H in or out of your timing can change the same kernel's "speedup" by an order of magnitude.
OpenMP GPU 的静默回退: 如果 offload 失败(没链上 libomptarget、没 GPU、编译目标不对),实现可以改在 CPU 上跑,程序照样「正确」。测加速比之前先 OMP_TARGET_OFFLOAD=mandatory,失败就失败,不要拿一个其实跑在主机上的数字去写报告。OpenMP GPU's silent fallback: if offload fails — libomptarget not linked, no GPU, wrong compile target — the implementation is allowed to run on the CPU instead, and the program is still "correct". Set OMP_TARGET_OFFLOAD=mandatory before measuring speedup; let it fail rather than reporting a number that was actually produced on the host.

4 · OpenMP:同一套 pragma,从多核接到 GPU4 · OpenMP: one set of pragmas, from multi-core out to the GPU

OpenMP 的卖点是增量并行:串行循环上插 pragma,编译器负责 outline 出线程或 device kernel。CPU 上 parallel for 管核;向量化用 simd;从 4.0/4.5 起,target 把同一思路接到加速器。课标「OpenMP(用于 GPU)」,指的就是后面这条,不是把 CPU OpenMP 再讲一遍。OpenMP sells incremental parallelism: add a pragma to a serial loop and the compiler outlines threads or a device kernel. On CPUs, parallel for handles cores and simd handles vectorisation; since 4.0/4.5, target extends the same idea to accelerators. When the syllabus says "OpenMP (for GPU)", it means that second part, not a second pass over CPU OpenMP.

GPU 上那串组合 pragma 可以按层次拆:The pragma stack on the GPU decomposes by level:

  1. target —— 把区域丢到设备,并建立一份 data environmenttarget — hand the region to the device and establish a data environment
    map(to: A[0:N]) 进、map(from: C[0:N]) 出。target data / enter data 用来避免每个循环都来回拷。map(to: A[0:N]) in, map(from: C[0:N]) out. target data / enter data avoid copying back and forth around every loop.
  2. teams —— 在设备上拉起一支 league,对应 CUDA gridteams — raise a league on the device, corresponding to a CUDA grid
    每个 team 有自己的 master。没有 teams,很多 GPU 运行时只能动到一小块计算单元。Each team has its own master. Without teams, many GPU runtimes can only reach a small fraction of the compute units.
  3. distribute —— 把外层迭代分给各个 teamdistribute — divide the outer iterations among teams
    只分到 team 一级,还没动 team 内部的线程。This only reaches the team level; the threads inside a team are still untouched.
  4. parallel for —— team 内部再切,对应 block 内的 threadsparallel for — subdivide within a team, corresponding to threads in a block
    常用合体:#pragma omp target teams distribute parallel for。二维循环再加 collapse(2)。The common composite: #pragma omp target teams distribute parallel for. Add collapse(2) for a two-dimensional loop.
#pragma omp target teams distribute parallel for \
    map(to: A[0:N], B[0:N]) map(from: C[0:N])
for (int i = 0; i < N; ++i)
    C[i] = A[i] + B[i];

Pin arrays to the device with target data outside the loop, then use several target regions inside that only map(tofrom:) what actually changes. LRZ's own OpenMP GPU lab is ordered the same way: get offload working first, then manage the data.

5 · CUDA:在 NVIDIA 上把控制权拿满5 · CUDA: taking full control on NVIDIA

CUDA 是这张表里控制粒度最细、可移植性最窄的一档。kernel 用 __global__ 写,发射用 <<<grid, block>>>,线程坐标是 blockIdx * blockDim + threadIdx。内存分成 global / shared / local / constant,shared memory 就是 block 级暂存,对应上面那张表的「组内共享」。CUDA is the finest-grained and least portable entry in this table. Kernels are written with __global__, launched with <<<grid, block>>>, and thread coordinates are blockIdx * blockDim + threadIdx. Memory divides into global / shared / local / constant, where shared memory is the block-level scratchpad — the "shared within a group" row of the table above.

  • 合并访存(coalescing)。 同一 warp 的线程读连续地址,硬件合成一次事务;按列读二维数组会把带宽打成碎片。这是 CUDA 实验里最稳的「架构相关」观察。Coalescing. When threads in a warp read consecutive addresses the hardware merges them into one transaction; reading a 2-D array by column shatters bandwidth. This is the most reliable architecture-dependent observation in a CUDA lab.
  • Occupancy ≠ 最快。 寄存器和 shared memory 用多用少,决定一个 SM 能常驻多少 warp。Occupancy 高有助于藏延迟,但不是目标函数;Nsight Compute 里看实际吞吐和 stall 理由。Occupancy ≠ fastest. How many registers and how much shared memory you use determines how many warps an SM can keep resident. High occupancy helps hide latency but is not the objective function; look at actual throughput and stall reasons in Nsight Compute.
  • Stream。 默认流是同步的。独立 stream 才能把 H2D、kernel、D2H 叠起来 —— 又回到「同步」那一节:你要显式决定哪些可以重叠。Streams. The default stream is synchronous. Only independent streams let H2D, kernel and D2H overlap — which returns to the synchronisation section: you decide explicitly what may overlap.
  • 统一内存。 cudaMallocManaged 让代码变短,page migration 的代价会写进第一次 touch。和 OpenMP -gpu=managed、SYCL USM shared 是同一类权衡。Unified memory. cudaMallocManaged makes the code shorter, and the cost of page migration lands on first touch. It is the same trade-off as OpenMP's -gpu=managed and SYCL's shared USM.

AMD 上的对位不是 CUDA,是 HIP(接口几乎一对一,后端换 ROCm)。课如果给 AMD GPU,不要硬套 nvcc;SYCL 或 OpenMP offload 往往比手写一份 CUDA、再指望 HIPIFY 更符合「评架构」的目标。On AMD the counterpart is not CUDA but HIP (a near one-to-one interface over the ROCm backend). If the course gives you an AMD GPU, do not force nvcc; SYCL or OpenMP offload usually fits the goal of evaluating architectures better than writing CUDA and hoping HIPIFY sorts it out.

6 · OpenCL:最「标准」,也最啰嗦6 · OpenCL: the most standard, and the most verbose

OpenCL 把异构计算拆成一条显式流水线:platform → device → context → queue → program → kernel → NDRange。kernel 用 OpenCL C 写成字符串或预编译的 SPIR-V,host 侧全是 C API。它能跑的地方最杂(GPU、CPU、历史上还有 FPGA),代价是启动一个 SAXPY 就要写几十行样板。OpenCL breaks heterogeneous compute into an explicit pipeline: platform → device → context → queue → program → kernel → NDRange. Kernels are written in OpenCL C as strings or precompiled SPIR-V, and the host side is all C API. It runs in the widest variety of places (GPUs, CPUs, historically FPGAs), at the price of dozens of lines of boilerplate to launch a SAXPY.

__kernel void add(__global const float* A,
                  __global const float* B,
                  __global float* C) {
    int i = get_global_id(0);
    C[i] = A[i] + B[i];
}

为什么课还要教它:因为 CUDA / SYCL / OpenMP offload 的设备侧执行模型,几乎都是从这套 NDRange 语义长出来的。get_global_id / get_local_id / get_group_id 对上 CUDA 的 threadIdx 三件套之后,后面换 API 只是换皮。新代码更常经 SYCL 或 OpenMP 到达设备;OpenCL 仍是「看见运行时到底在干什么」的底图,也是某些非 NVIDIA 设备上仍能找到的最低公共 API。Why teach it anyway: because the device-side execution model of CUDA, SYCL and OpenMP offload all grew out of these NDRange semantics. Once get_global_id / get_local_id / get_group_id line up with CUDA's threadIdx trio, switching APIs later is mostly cosmetic. New code more often reaches the device through SYCL or OpenMP; OpenCL remains the base map for seeing what the runtime is really doing, and on some non-NVIDIA devices it is still the lowest common API available.

7 · SYCL:单源 C++,后端再接各家7 · SYCL: single-source C++, backends underneath

SYCL 的承诺是:一份现代 C++ ,kernel 就写在 lambda 里,由实现接到 CUDA、HIP、Level Zero 或 OpenCL。Intel DPC++(icpx -fsycl)和 AdaptiveCpp(原 hipSYCL)是课上最可能碰到的两套。SYCL 2020 起有两条数据路:SYCL's promise: one piece of modern C++ with the kernel written inline as a lambda, mapped by the implementation onto CUDA, HIP, Level Zero or OpenCL. Intel DPC++ (icpx -fsycl) and AdaptiveCpp (formerly hipSYCL) are the two you are most likely to meet. Since SYCL 2020 there are two data paths:

Buffer + accessor

运行时根据 accessor 的读写意图建 DAG,自己插入拷贝。安全、啰嗦少一些,调试时要习惯「这次 accessor 到底触发了一次 H2D 没有」。The runtime builds a DAG from the read/write intent of your accessors and inserts the copies itself. Safer and less verbose, though when debugging you have to develop a feel for whether a given accessor triggered an H2D or not.

USM

malloc_device / malloc_shared / malloc_host。指针语义接近 CUDA。device 指针不能在 host 解引用;shared 可以,但迁移成本和 managed CUDA 同类。malloc_device / malloc_shared / malloc_host. The pointer semantics are close to CUDA's. A device pointer cannot be dereferenced on the host; a shared one can, with migration costs comparable to CUDA managed memory.

q.parallel_for(N, [=](sycl::id<1> i) {
    C[i] = A[i] + B[i];
}).wait();

SYCL 不是「CUDA 的开源版」。它在 Intel GPU 上是一等公民,在 NVIDIA / AMD 上取决于你的编译器有没有把对应 backend 编进来。课上换节点时,第一件事是 sycl-ls(或实现提供的 device 列表)确认 queue 绑的是你以为的那块设备,而不是偷偷落到 OpenCL CPU 回退。SYCL is not "open-source CUDA". It is a first-class citizen on Intel GPUs; on NVIDIA and AMD it depends on whether your compiler was built with the matching backend. When you move to a new node, the first thing to run is sycl-ls (or the implementation's device list) to confirm the queue is bound to the device you think it is, rather than quietly falling back to an OpenCL CPU.

同一算法、换节点,才是这门课的单位。 厂商短讲听的是「这块硅片的向量宽、缓存、HBM、互联」。报告里要对齐的是:问题规模、是否含拷贝、编译器旗标、绑核(OMP_PROC_BIND / OMP_PLACES)、以及设备到底是不是你以为的那一块。GFLOP/s 单独出现没有对照价值。The unit of this course is one algorithm across different nodes. Vendor talks are about a chip's vector width, caches, HBM and interconnect. What a report has to align on is: problem size, whether copies are included, compiler flags, pinning (OMP_PROC_BIND / OMP_PLACES), and whether the device really is the one you think. A GFLOP/s figure on its own has nothing to compare against.

10 · 上课前我给自己的清单10 · My own checklist before the course

  • 能把 team / block / work-group 画在同一层,不靠背定义。Be able to draw team / block / work-group on the same level without reciting definitions.
  • CPU 上先看向量化报告,再谈 OpenMP 线程数;线程数 × SIMD 宽度才是峰值口径。On CPUs, read the vectorisation report before discussing thread counts; peak is thread count × SIMD width.
  • GPU 上先证明 kernel 跑在设备上,再谈快慢。mandatory offload、SYCL device 列表、CUDA nvidia-smi 是三种等价的「别骗自己」。On GPUs, prove the kernel ran on the device before discussing speed. mandatory offload, the SYCL device list and CUDA's nvidia-smi are three equivalent ways of not fooling yourself.
  • 计时拆三截:H2D、kernel、D2H。加速比要写清楚包不包含搬运。Split timing three ways: H2D, kernel, D2H. State clearly whether the speedup includes the transfers.
  • 同步实验优先做 reduction / false sharing / barrier 的代价,而不是再写一把大 critical。For synchronisation, measure the cost of reduction, false sharing and barriers rather than writing yet another big critical.
  • 可移植性实验:同一份 OpenMP 或 SYCL,在 NVIDIA 和 Intel/AMD 节点上编过去 —— 这比在一块卡上把 CUDA occupancy 调到理论峰值,更贴近 BEAST 存在的理由。Portability experiment: compile the same OpenMP or SYCL on both an NVIDIA and an Intel/AMD node — closer to why BEAST exists than tuning CUDA occupancy to the theoretical peak on one card.
