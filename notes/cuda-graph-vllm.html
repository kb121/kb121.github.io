CUDA Graph 详解 & vLLM 里的 CUDA Graph 与精度CUDA Graph Explained & CUDA Graph in vLLM + Precision

这篇笔记用图文 + 动图讲清三件事:① CUDA Graph 到底是什么、为什么能加速;② vLLM 里怎么用 CUDA Graph(piecewise / full);③ vLLM 里 CUDA Graph 模式 vs Eager 模式对精度的影响。基于 vLLM V1 引擎。This note uses figures and animations to settle three things: ① what CUDA Graph actually is and why it speeds things up, ② how vLLM uses CUDA Graph (piecewise vs full), and ③ how graph mode compares with eager mode on numerical accuracy. Based on the vLLM V1 engine.

一句话总览: CUDA Graph = 把一连串 GPU kernel 录制成一张图,之后一次发射、整图重放,省掉每个 kernel 的 CPU 发射开销。它对 decode 阶段(大量小 kernel、访存密集)提速最明显。vLLM 默认用 FULL_AND_PIECEWISE(decode 用整图、prefill/混合用分段图)。CUDA Graph 本身不改数值,真正带来微小精度差异的是与之配套的 torch.compile(算子融合)和 batch padding。In one line: a CUDA Graph records a run of GPU kernels into a graph, then launches and replays the whole thing at once, eliminating the per-kernel CPU launch cost. The gain is largest in decode, where kernels are many, small and memory-bound. vLLM defaults to FULL_AND_PIECEWISE — a full graph for decode, piecewise graphs for prefill and mixed batches. The graph itself does not change any numbers; the tiny differences people observe come from the torch.compile that accompanies it (operator fusion) and from batch padding.

0 · 先看一眼"问题"0 · The problem, first

GPU 跑一个 kernel,需要 CPU 先"发射(launch)"它 —— 这一步有固定开销(几微秒)。LLM 的一个 decode step 要串行跑成百上千个小 kernel(每层的 norm、QKV 投影、MLP、残差…)。当 batch 很小,单个 kernel 在 GPU 上跑得比 CPU 发射下一个还快,GPU 就只能干等 —— 这叫 CPU launch-bound。下面这张动图就是这个浪费:Running a kernel on the GPU requires the CPU to launch it, and that has a fixed cost of a few microseconds. One LLM decode step runs hundreds or thousands of small kernels back to back (per-layer norm, QKV projection, MLP, residual, and so on). At small batch sizes a single kernel finishes on the GPU faster than the CPU can launch the next one, so the GPU sits idle — this is being CPU launch-bound. The animation below is that waste:

1 · CUDA Graph 是什么1 · What a CUDA Graph is

CUDA Graph 的思路非常直接:既然每次 decode step 跑的 kernel 序列几乎一模一样,那就把它录制(capture)成一张静态图,之后每步只发射这一张图、让 GPU 一口气重放(replay)所有 kernel,中间不再回到 CPU。The idea is direct: since every decode step runs almost exactly the same kernel sequence, capture it once as a static graph, then launch just that graph each step and let the GPU replay every kernel in one go without returning to the CPU.

为什么对 LLM decode 特别有效? Decode 每步只生成 1 个 token,是 访存密集 + 小 batch:kernel 又多又小、发射开销占比高。CUDA Graph 正好把这部分开销抹平。反观 prefill:一次算很多 token,kernel 本身就跑得久,发射开销占比小,收益没那么大。Why is this so effective for LLM decode? Decode produces one token per step and is memory-bound at small batch: many small kernels, so launch overhead dominates. CUDA Graph erases exactly that. Prefill is the opposite — it computes many tokens at once, the kernels run long enough that launch overhead is a small fraction, and the gain is modest.

2 · CUDA Graph 的代价与约束2 · The costs and constraints

收益 Gains

  • 消除每个 kernel 的 CPU 发射开销,decode 延迟显著下降。Removes the per-kernel CPU launch cost, cutting decode latency noticeably.
  • GPU 利用率拉满,小 batch 场景尤其明显。Keeps GPU utilisation high, especially at small batch.

约束 Constraints

  • 静态形状:图固化了张量形状和显存地址,batch / 序列长度一变就得换一张图。Static shapes: the graph freezes tensor shapes and memory addresses, so any change in batch or sequence length needs a different graph.
  • 无动态控制流:图里跳过所有 CPU 逻辑(if / print / Python 分支),只重放 GPU 算子。No dynamic control flow: the graph skips all CPU logic (if, print, Python branches) and replays only GPU operators.
  • 额外显存 + 启动耗时:每张捕获的图都要占显存,启动时 warmup 也要时间。Extra memory and startup time: every captured graph costs memory, and warmup costs time at startup.

3 · vLLM 里的 CUDA Graph3 · CUDA Graph inside vLLM

LLM 模型里,注意力用的是 FlashAttention 这类专用 kernel,形状多变、对整图捕获不友好;而 非注意力部分(LayerNorm、MLP、残差、logits 投影)规整、好捕获。vLLM 据此提供了 分段(piecewise) 和 整图(full) 两种思路,并建立在 torch.compile 的分段编译之上。In an LLM, attention runs specialised kernels like FlashAttention whose shapes vary and which capture poorly; the non-attention parts (LayerNorm, MLP, residual, logits projection) are regular and capture well. vLLM therefore offers both piecewise and full graphs, built on top of torch.compile's piecewise compilation.

vLLM V1 用一个 cudagraph_mode 开关统一管理这套策略,共 5 种模式:vLLM V1 manages all of this through one cudagraph_mode switch with five settings:

cudagraph_mode含义Meaning适用When to use
NONE完全关闭 CUDA Graph(= eager)CUDA Graph fully off (= eager)调试 / 显存实验Debugging / memory experiments
PIECEWISE只用分段图,注意力等不兼容算子留 eagerPiecewise only; attention and other incompatible operators stay eager通用、最灵活General-purpose, most flexible

FULL_AND_PIECEWISE 默认FULL_AND_PIECEWISE defaultdecode 批用整图,prefill / 混合批用分段图Full graph for decode, piecewise for prefill and mixed batches大多数模型最优Best for most models
默认 FULL_AND_PIECEWISE 的巧思:decode 阶段对延迟最敏感 → 用整图把发射开销压到最低(降 ITL,即 token 间延迟);prefill / 混合阶段形状多变 → 用分段图保住灵活性和较小的 TTFT。两全其美。Why FULL_AND_PIECEWISE is a smart default: decode is the latency-sensitive phase → a full graph drives launch overhead to a minimum (lower ITL, the inter-token latency); prefill and mixed batches have varying shapes → piecewise graphs preserve flexibility and a decent TTFT. Both ends covered.

4 · 形状离散化与 padding4 · Shape discretisation and padding

CUDA Graph 要静态形状,但运行时 batch 大小千变万化。vLLM 的做法:只为一组预设的 batch size 捕获图(cudagraph_capture_sizes,如 1、2、4、8…),运行时把实际 batch 向上 padding 到最近的捕获尺寸,多出来的是 dummy 行,算完丢弃。CUDA Graph wants static shapes, but runtime batch sizes vary constantly. vLLM's answer: capture graphs only for a preset list of batch sizes (cudagraph_capture_sizes, e.g. 1, 2, 4, 8…) and at runtime pad the actual batch up to the nearest captured size. The extra rows are dummies and get discarded.

5 · CUDA Graph vs Eager:对精度的影响5 · CUDA Graph vs eager: the accuracy question

这是最容易被误解的一节。先把结论摆出来,再拆开讲:This is the most misunderstood part. Conclusion first, then the details:

结论:CUDA Graph 本身不改变数值 —— 它重放的是和 eager 完全相同的 kernel,输入相同,输出逐比特相同。vLLM 里看到的 "graph 模式 vs eager 模式" 的细微差异,主要来自和 graph 配套的 torch.compile(算子融合、中间精度、kernel 选择),以及 padding 是否被正确 mask。Conclusion: CUDA Graph does not change numbers — it replays exactly the same kernels as eager, so identical inputs give bit-identical outputs. The small differences people see between "graph mode and eager mode" in vLLM come mainly from the torch.compile that ships with it (fusion, intermediate precision, kernel selection) and from whether padding is masked correctly.

不会改数值的部分 What does not change numbers

纯 CUDA Graph 的"录制 → 重放":同样的 kernel、同样的顺序、同样的地址。重放 = 把 eager 那次执行原样再放一遍,数值逐比特一致。Pure capture-and-replay: same kernels, same order, same addresses. A replay is the eager execution played back verbatim, and the values are bit-identical.

可能带来差异的部分 What can differ

  • torch.compile 融合:把多个算子融成一个 kernel,中间结果的累加顺序 / 精度变了 → 末位级差异。torch.compile fusion: several operators become one kernel, changing accumulation order and intermediate precision → last-bit differences.
  • kernel 选择:编译后可能选了不同实现(不同 tiling / 算法)。Kernel selection: compilation may pick a different implementation (different tiling or algorithm).
  • padding 处理:dummy 行若没 mask 干净,可能影响 reduce / 归一化。Padding handling: dummy rows that are not masked cleanly can perturb reductions and normalisations.
差异有多大? 通常是浮点末位级(在 fp16/bf16 容差内),极少改变最终采样出的 token;贪心解码下偶尔可能在某些 step 选到不同 token(累积效应),采样解码下基本是噪声级。PyTorch 官方口径:eager 与 compile 之间存在小数值差异是预期之内的,判断对错应与 fp64 参考比较,而非要求和 fp16 eager 逐比特相等。How big is the difference? Usually last-bit floating point, within fp16/bf16 tolerance, and it rarely changes the sampled token. Under greedy decoding it can occasionally pick a different token at some step through accumulation; under sampling it is essentially noise. PyTorch's official position is that small numerical differences between eager and compile are expected, and correctness should be judged against an fp64 reference rather than by demanding bit-equality with fp16 eager.
实战调试法:Debugging in practice:怀疑精度问题(输出变差、复现某个 bug)时,第一步加 --enforce-eager 关掉 CUDA Graph + 编译,拿到"参考数值"做 A/B:When you suspect an accuracy problem — degraded output, or reproducing a bug — the first move is --enforce-eager to turn off CUDA Graph and compilation, giving you reference numbers to A/B against:
  • 加上后问题消失 → 差异来自 compile/graph 路径,多半是融合或 padding mask,可接受或针对性修。Problem disappears with it → the difference is on the compile/graph path, most likely fusion or a padding mask; either acceptable or fixable specifically.
  • 加上后问题还在 → 跟 CUDA Graph 无关,去查模型 / 权重 / 量化 / 输入。Problem persists → nothing to do with CUDA Graph; go look at the model, weights, quantisation or inputs.

6 · Eager / 编译 / CUDA Graph 的关系与性能6 · How eager, compilation and CUDA Graph relate, and what each is worth

很多人把 eager、torch.compile(图模式编译)、CUDA Graph 并列,以为是三选一。其实它们不在同一个维度上 —— 是两条正交的轴:一条管"跑哪些 kernel"(编译层),一条管"怎么发射这些 kernel"(下发层)。People often line up eager, torch.compile and CUDA Graph as three alternatives to choose between. They are not on the same axis. There are two orthogonal axes: one decides "which kernels run" (the compilation layer), the other decides "how those kernels are launched" (the dispatch layer).

比较Comparison关系Relationship为什么Why
Eager ↔ torch.compile并行(同层二选一)Parallel (same layer, pick one)都在编译层,回答同一个问题:跑原始 kernel 还是融合后的 kernel,互斥Both live in the compilation layer and answer the same question — original kernels or fused ones. Mutually exclusive.
compile ↔ CUDA Graph上下(先后,可叠加)Stacked (sequential, composable)compile 先产出 kernel(上游),CUDA Graph 再把它们的发射打包(下游)compile produces the kernels (upstream), CUDA Graph then packages their launches (downstream)
Eager ↔ CUDA Graph上下(不同层)Stacked (different layers)CUDA Graph 不关心上游是 eager 还是 compile,只负责重放定好的 kernelCUDA Graph does not care whether upstream was eager or compiled; it only replays the kernels already chosen

什么时候谁更重要?Which matters more, and when?
  • 小 batch / decode(launch-bound):瓶颈是 CPU 发射开销 → CUDA Graph 是最大的杠杆(③相比①已大幅提升)。Small batch / decode (launch-bound): the bottleneck is CPU launch overhead → CUDA Graph is the biggest lever (③ alone is already far ahead of ①).
  • 大 batch / prefill(compute-bound):kernel 本身就跑得久、发射占比小 → kernel 质量(compile 融合)更重要,CUDA Graph 收益变小。Large batch / prefill (compute-bound): kernels run long and launch is a small fraction → kernel quality (compile fusion) matters more, and CUDA Graph's gain shrinks.
  • 所以 vLLM 默认 ④ compile + CUDA Graph:两边通吃。两层全关(--enforce-eager)只在调试 / 显存紧张 / backend 不支持时用。Hence vLLM's default of ④ compile + CUDA Graph, which covers both. Turning both layers off (--enforce-eager) is for debugging, tight memory, or a backend that cannot capture.

7 · 实操速查7 · Quick reference

# 默认就是 FULL_AND_PIECEWISE,通常无需手动设
vllm serve Qwen/Qwen2.5-7B-Instruct

# 显式指定 cudagraph 模式
vllm serve MODEL --compilation-config '{"cudagraph_mode": "FULL_AND_PIECEWISE"}'
# 可选值: NONE | PIECEWISE | FULL | FULL_DECODE_ONLY | FULL_AND_PIECEWISE

# 纯 eager:关闭 CUDA Graph + torch.compile(调试 / 显存实验 / 拿参考数值)
vllm serve MODEL --enforce-eager

# 自定义捕获的 batch 尺寸(影响显存与命中率)
vllm serve MODEL --compilation-config '{"cudagraph_capture_sizes": [1,2,4,8,16,32]}'# FULL_AND_PIECEWISE is the default; usually nothing to set
vllm serve Qwen/Qwen2.5-7B-Instruct

# Set the cudagraph mode explicitly
vllm serve MODEL --compilation-config '{"cudagraph_mode": "FULL_AND_PIECEWISE"}'
# Options: NONE | PIECEWISE | FULL | FULL_DECODE_ONLY | FULL_AND_PIECEWISE

# Pure eager: no CUDA Graph, no torch.compile (debugging / memory / reference numbers)
vllm serve MODEL --enforce-eager

# Customise the captured batch sizes (affects memory and hit rate)
vllm serve MODEL --compilation-config '{"cudagraph_capture_sizes": [1,2,4,8,16,32]}'
什么时候用 --enforce-eager? ① 调试数值/精度;② 显存非常紧张,不想为捕获图额外占显存;③ 用的 attention backend 不支持图捕获;④ 频繁变化的奇异形状导致图反复 miss。其余情况保持默认(开图)就好,性能更优。When should you use --enforce-eager? ① debugging numbers or accuracy; ② memory is very tight and you do not want to spend it on captured graphs; ③ the attention backend cannot capture graphs; ④ constantly shifting odd shapes make the graphs miss repeatedly. Otherwise keep the default (graphs on) — it is faster.
