从 0 到 1 写一个 Triton GEMM,再一步步调快A Triton GEMM from Scratch, Then Tuned Step by Step

这篇按真实的调优顺序走一遍:先建立「一个 program 负责一块 tile,而不是一个标量」的心智模型, 写出能跑但很慢的第一版;然后每次只改一件事 —— 补边界、换发射顺序、开软件流水、交给 autotune —— 看每一步各自解决了什么瓶颈。最有意思的一步一行计算都没改,只是换了 program 的编号方式。This note walks the real tuning order: first build the mental model that one program owns a tile, not a scalar, and write a first version that runs but is slow; then change exactly one thing at a time — add bounds handling, change the launch order, turn on software pipelining, hand it to autotune — and see what each step actually fixes. The most interesting step changes not a single line of computation; it only renumbers the programs.

一、先换脑子:program 是 tile,不是 thread1 · Rewire first: a program is a tile, not a thread

写 CUDA 时你操心的是「这个线程算哪个元素」,于是要手写 shared memory 搬运、bank conflict、 __syncthreads()。Triton 把抽象层级抬高了一级:你操心的是「这个 program 算哪一块」, 块内的向量化、寄存器分配、共享内存排布交给编译器。In CUDA you worry about which element this thread computes, which means writing shared-memory staging, bank conflicts and __syncthreads() by hand. Triton raises the abstraction one level: you worry about which tile this program computes, and vectorisation, register allocation and shared-memory layout within the tile are the compiler's problem.

索引、边界、共享内存搬运、同步,全部手写。控制力最强,心智负担也最大。Indexing, bounds, shared-memory staging and synchronisation, all by hand. Maximum control, maximum cognitive load.
Triton:你管到每个 tileTriton: you manage every tile
tl.program_id → 一整块 [BLOCK_M, BLOCK_N]tl.program_id → a whole [BLOCK_M, BLOCK_N]
你只写「取这块、乘、累加」,块内怎么排布由编译器决定。少写九成代码,但也少了九成微调余地。You write only "fetch this block, multiply, accumulate"; how it is laid out inside the block is the compiler's call. Ninety percent less code, and ninety percent less room to micro-tune.
这个差别决定了后面所有优化的形态:在 Triton 里你能调的不是「线程怎么排」,而是块多大、块按什么顺序发射、流水开几级。That difference shapes every optimisation below: what you can tune in Triton is not how threads are arranged but how big the blocks are, in what order they launch, and how many pipeline stages to run.

二、v0:先让它跑起来2 · v0: make it run first

GEMM 的分块形式很直白:每个 program 负责 C 的一个 [BLOCK_M, BLOCK_N] tile, 沿 K 方向循环,每次取 A 的一个 [BLOCK_M, BLOCK_K] 和 B 的一个 [BLOCK_K, BLOCK_N], 乘完累加进去。整个主循环只有三句话。The tiled form of GEMM is straightforward: each program owns one [BLOCK_M, BLOCK_N] tile of C, loops along K, taking a [BLOCK_M, BLOCK_K] of A and a [BLOCK_K, BLOCK_N] of B each time, multiplying and accumulating. The whole main loop is three statements.

注意 C 那块自始至终不动 —— 它一直待在寄存器里的累加器上,只有 A、B 在沿 K 滑动。这就是分块 GEMM 省访存的根本原因。Notice that the C block never moves — it lives in an accumulator in registers the whole time, and only A and B slide along K. This is fundamentally why tiled GEMM saves memory traffic. 
@triton.jit
def matmul_kernel(a_ptr, b_ptr, c_ptr, M, N, K,
                  stride_am, stride_ak, stride_bk, stride_bn,
                  stride_cm, stride_cn,
                  BLOCK_SIZE_M: tl.constexpr,
                  BLOCK_SIZE_N: tl.constexpr,
                  BLOCK_SIZE_K: tl.constexpr):
    # v0:最朴素的行优先映射,一个 program 一个 C tile
    pid = tl.program_id(axis=0)
    grid_n = tl.cdiv(N, BLOCK_SIZE_N)
    pid_m = pid // grid_n
    pid_n = pid % grid_n

    offs_am = pid_m * BLOCK_SIZE_M + tl.arange(0, BLOCK_SIZE_M)
    offs_bn = pid_n * BLOCK_SIZE_N + tl.arange(0, BLOCK_SIZE_N)
    offs_k = tl.arange(0, BLOCK_SIZE_K)
    a_ptrs = (a_ptr + offs_am[:, None] * stride_am
                    + offs_k[None, :] * stride_ak)
    b_ptrs = (b_ptr + offs_k[:, None] * stride_bk
                    + offs_bn[None, :] * stride_bn)

    acc = tl.zeros((BLOCK_SIZE_M, BLOCK_SIZE_N), dtype=tl.float32)
    for k in range(0, tl.cdiv(K, BLOCK_SIZE_K)):
        a = tl.load(a_ptrs)
        b = tl.load(b_ptrs)
        acc = tl.dot(a, b, acc)          # ← 落到 Tensor Core
        a_ptrs += BLOCK_SIZE_K * stride_ak
        b_ptrs += BLOCK_SIZE_K * stride_bk

    c = acc.to(tl.float16)
    offs_cm = pid_m * BLOCK_SIZE_M + tl.arange(0, BLOCK_SIZE_M)
    offs_cn = pid_n * BLOCK_SIZE_N + tl.arange(0, BLOCK_SIZE_N)
    c_ptrs = (c_ptr + stride_cm * offs_cm[:, None]
                    + stride_cn * offs_cn[None, :])

这版能出正确结果,但有两个前提:M、N、K 都得能被块大小整除,否则会越界读写。先补上这个。This version produces correct results, but only on two conditions: M, N and K must all divide evenly by the block sizes, or it reads and writes out of bounds. Fix that first.

三、v1:两个必修补丁 —— 边界与精度3 · v1: two mandatory patches — bounds and precision

边界。 真实的 shape 不会那么听话。Triton 的做法是给 tl.load 加 mask, 越界的位置填 0(填 0 对乘加是安全的,不影响结果);写回时同样用 mask 挡住越界行列:Bounds. Real shapes are not that obliging. Triton's answer is a mask on tl.load, filling out-of-range positions with 0 (safe for multiply-accumulate, and it does not change the result); the store is masked the same way against out-of-range rows and columns:

# K 方向:最后一个块可能不满,越界处填 0
    a = tl.load(a_ptrs,
                mask=offs_k[None, :] < K - k * BLOCK_SIZE_K, other=0.0)
    b = tl.load(b_ptrs,
                mask=offs_k[:, None] < K - k * BLOCK_SIZE_K, other=0.0)

    # 写回:M、N 两个方向都要挡
    c_mask = (offs_cm[:, None] < M) & (offs_cn[None, :] < N)
    tl.store(c_ptrs, c, mask=c_mask)# Along K: the last block may be partial, out-of-range filled with 0
    a = tl.load(a_ptrs,
                mask=offs_k[None, :] < K - k * BLOCK_SIZE_K, other=0.0)
    b = tl.load(b_ptrs,
                mask=offs_k[:, None] < K - k * BLOCK_SIZE_K, other=0.0)

    # Store: both M and N need guarding
    c_mask = (offs_cm[:, None] < M) & (offs_cn[None, :] < N)
    tl.store(c_ptrs, c, mask=c_mask)

精度。 上面 acc 已经声明成 tl.float32 了,这不是随手写的。 输入是 fp16/bf16,但累加必须在 fp32 上做 —— K 有几千轮,用 fp16 累加会一路吃掉低位,误差肉眼可见。 正确姿势是整个 K 循环都用 fp32 累加,循环结束后再转回 fp16。顺带一提, 如果要融激活函数,也应该在转换之前做,精度更好还省一次读写。Precision. The acc above is already declared tl.float32, and that was not casual. The inputs are fp16/bf16, but the accumulation has to happen in fp32 — with thousands of K iterations, accumulating in fp16 eats the low bits all the way down and the error becomes visible. The correct form is to accumulate in fp32 through the whole K loop and convert back to fp16 afterwards. Incidentally, if you are fusing an activation, do it before the conversion: better precision, and one fewer round trip.

四、v2:只改发射顺序,不改一行计算4 · v2: change only the launch order, not one line of computation

这是整条优化路径上性价比最高的一步。v0 用的是行优先映射:pid_m = pid // grid_n。 问题在于,相邻的 program 几乎同时在跑,而行优先意味着它们横着扫过 C 的一整行 —— 这些 program 共享同一行 A,但要用掉所有列的 B。B 把 L2 冲刷了一遍,复用率极差。This is the highest-return step on the whole path. v0 uses a row-major mapping: pid_m = pid // grid_n. The problem is that adjacent programs run at roughly the same time, and row-major means they sweep across an entire row of C — those programs share one row of A but consume every column of B. B flushes L2 once through, and reuse is terrible.

换个编号方式:先在纵向吃满 GROUP_SIZE_M 行,再往右挪一列。同时在跑的 program 就聚成了一个方块, A 和 B 的加载量都降下来。下面这张图可以自己拖:Renumber them: fill GROUP_SIZE_M rows vertically first, then move one column right. The concurrently running programs now cluster into a square, and the load volume drops for both A and B. The figure below is draggable:

收益有多大?官方文档给的是在某些架构上超过 10%(A100 上 220 → 245 TFLOPS)。 PyTorch 团队在 MoE 的 grouped GEMM 里报告过更极端的情况:1.33 倍加速,L2 命中率 +60%。 差异这么大,是因为收益完全取决于矩阵形状和 L2 容量的比例关系 —— 所以 GROUP_SIZE_M 该设多少,最后还是得实测。How much does it buy? The docs say over 10% on some architectures (220 → 245 TFLOPS on A100). The PyTorch team reported something more extreme in a MoE grouped GEMM: 1.33× speedup and +60% L2 hit rate. The spread is that wide because the gain depends entirely on the ratio between matrix shape and L2 capacity — so what GROUP_SIZE_M should be still comes down to measurement.

五、v3:num_stages —— 让搬运和计算重叠5 · v3: num_stages — overlapping movement with computation

到这一步,数据的去向已经优化好了,但时机还没有。 v0 的循环是严格串行的:取 A、取 B、算,再取下一块。从 HBM 取数要几百个周期,这期间 Tensor Core 完全闲着。By this point the destination of the data is optimised, but the timing is not. v0's loop is strictly serial: fetch A, fetch B, compute, then fetch the next block. A fetch from HBM takes hundreds of cycles, and the Tensor Cores sit idle throughout.

解法是软件流水:算第 k 块的同时,把第 k+1 块预取到共享内存。 Triton 不用你手写,给 num_stages 一个大于 1 的值,编译器会自动做循环展开与异步拷贝插入。The fix is software pipelining: prefetch block k+1 into shared memory while computing block k. Triton does not make you write it — give num_stages a value above 1 and the compiler unrolls the loop and inserts the asynchronous copies.

上排每算一块都要先干等一次搬运(斜纹为空转);下排把搬运藏到了上一块的计算背后,Tensor Core 基本不断流。 代价是共享内存要同时装下多级缓冲,所以 num_stages 不能无限加 —— 开太大会因 SMEM 不够而降低 occupancy,反而变慢。The top row waits for a transfer before every block (hatched cells are idle); the bottom row hides the transfer behind the previous block's computation, keeping the Tensor Cores essentially fed. The cost is that shared memory must hold several buffers at once, so num_stages cannot grow without limit — too large and insufficient SMEM lowers occupancy, making it slower instead.

七、天花板之上:persistent、TMA 与 warp 专业化7 · Above the ceiling: persistent kernels, TMA and warp specialisation

上面几步做完,通常已经能摸到 cuBLAS 的量级。再往上就要动执行模型本身了,这几项都依赖较新的硬件:With the steps above done you are usually in cuBLAS territory. Going further means changing the execution model itself, and these all depend on newer hardware:

  • Persistent kernel —— 不再「一个 tile 一个 CTA」,而是发射恰好等于 SM 数量的 program,每个在内部循环领取多个 tile。省掉大量 CTA 启动与调度开销,也让流水能跨 tile 摊薄。注意官方教程提到:persistent 化之后 L2 命中率反而会掉约 10%,因此仍需在 tile 调度器里做分组,和动图 3 是同一个道理。Persistent kernel — instead of one CTA per tile, launch exactly as many programs as there are SMs and have each claim multiple tiles in an inner loop. This removes a great deal of CTA launch and scheduling overhead and lets the pipeline amortise across tiles. Note the tutorial's caveat: going persistent drops L2 hit rate by around 10%, so you still need grouping in the tile scheduler — the same reasoning as Figure 3.
  • TMA(Tensor Memory Accelerator) —— Hopper 起的硬件搬运引擎。用 tl.make_block_ptr 或 tensor descriptor,编译器能发出异步的批量拷贝,还省掉对齐 tile 的越界 mask 开销。TMA (Tensor Memory Accelerator) — a hardware transfer engine from Hopper onward. With tl.make_block_ptr or a tensor descriptor, the compiler can emit asynchronous bulk copies and skip the bounds-mask overhead for aligned tiles.
  • Warp 专业化 —— 把一个 CTA 里的 warp 分工:生产者 warp 组专职搬数,消费者 warp 组专职算。开关是 warp_specialize=True。官方在 09 号教程里同时给了 naive / persistent / TMA / descriptor 几个版本可以对拍。Warp specialisation — divide labour among the warps in a CTA: producer warps move data, consumer warps compute. The switch is warp_specialize=True. Tutorial 09 ships naive / persistent / TMA / descriptor variants side by side for comparison.

01
先改变量,再改代码Change the variables before changing the code

Triton 里最见效的往往不是重写计算,而是改「块多大、按什么顺序发、流水开几级」。v2 那一步计算逻辑一字未动,只换了 pid 到 tile 的映射函数。What pays off most in Triton is usually not rewriting the computation but changing how big the blocks are, in what order they launch, and how many pipeline stages run. Step v2 left the computation untouched and only swapped the pid-to-tile mapping.

02
fp32 累加器不是可选项An fp32 accumulator is not optional

输入 fp16/bf16、累加 fp32、循环结束再转回去。K 上千轮的累加用低精度会明显掉点,而 tl.dot 本来就支持 fp32 累加,不花额外代价。Inputs in fp16/bf16, accumulate in fp32, convert back after the loop. Accumulating thousands of K iterations at low precision visibly costs accuracy, and tl.dot supports fp32 accumulation at no extra cost anyway.

03
发射顺序就是缓存策略Launch order is a caching policy

你无法直接控制 L2 装什么,但能控制 program 的执行次序,而次序决定了同时活跃的数据集有多大。9×9 的例子里,这个选择就是 90 块和 54 块的差别。You cannot control what goes into L2 directly, but you can control the execution order of the programs, and that order determines how large the concurrently live working set is. In the 9×9 example, that choice is the difference between 90 blocks and 54.

04
每个旋钮都有反向代价Every knob has a cost in the other direction

块调大提高算术强度但压 occupancy,num_stages 调大掩盖延迟但吃 SMEM。没有普适最优解,这正是要 autotune 的原因。Larger blocks raise arithmetic intensity but squeeze occupancy; a larger num_stages hides latency but eats SMEM. There is no universal optimum, which is exactly why autotune exists.

05
autotune 要预热Autotune needs warming up

它是在真实 shape 上实测选优的。不 warm up,第一个请求就会被搜索过程拖成长尾;shape 抖动大的场景还要考虑分桶。It selects by measuring on the real shape. Without a warm-up the first request gets dragged into the tail by the search; shape-jittery workloads should also consider bucketing.

06
先量瓶颈,再挑手段Measure the bottleneck before picking a remedy

访存受限就上流水和 TMA,L2 抖动就调分组,启动开销高就上 persistent。顺序反了会做很多无用功 —— 这也是本文按这个顺序排列的原因。Memory-bound calls for pipelining and TMA, L2 thrash calls for grouping, high launch overhead calls for persistent kernels. Getting the order backwards wastes a lot of effort — which is why this note is ordered the way it is.
