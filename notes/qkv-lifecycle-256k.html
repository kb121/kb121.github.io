Q / K / V 在 256K 对话窗口中的一生The Life of Q / K / V in a 256K Chat Window

同一个聊天窗口里持续对话,直到上下文用满 262,144 token。这个过程中 Query 每一步都被造出来又立刻丢弃, 而 Key / Value 只增不减,一路堆到 80 GiB 显存。下面用三段动画把这件事拆开看。

层数 80 Q 头 64 KV 头 8 (GQA) head_dim 128 hidden 4096 上下文 262,144 dtype bf16

一、三个张量,两种命运

Q、K、V 都由同一个 token 的隐状态线性投影而来,但它们在时间轴上的行为完全不同: Q 是「一次性」的,K/V 是「永久」的。这个区别决定了长上下文推理的全部工程难点。

Q
Query · 瞬时

我现在想找什么

只属于「当前正在计算的那些 token」。算完这一层的 attention 就被释放,不进缓存、不跨步复用。序列再长,Q 也不会变大。

q_proj: 4096 → 64 × 128 = 8192
生命周期:单层单步,用完即弃
K
Key · 累积

历史里都有什么

每个 token 算一次,然后永久写进 KV cache。后续每生成一个 token,都要把整条历史的 K 重新读一遍算注意力分数。

k_proj: 4096 → 8 × 128 = 1024
生命周期:写入后常驻,直到会话结束
V
Value · 累积

取到之后拿走什么

与 K 完全同步地累积。注意力权重算好后,用它对全部历史 V 做加权求和。K 和 V 一起构成 KV cache 的两半。

v_proj: 4096 → 8 × 128 = 1024
生命周期:写入后常驻,直到会话结束

GQA:64 个 Q 头,只养 8 份 K/V

每组 8 个 Query 头共享同一份 Key/Value。KV cache 因此比 MHA 小 8 倍 —— 这是 256K 上下文能跑起来的前提。 鼠标划过任意一组看分组关系。

8 组 × (1 份 KV + 8 个 Q 头)  ·  若用 MHA 则需 64 份 KV,cache 将达 640 GiB

四、代价曲线

KV cache 随上下文线性增长,而 decode 吞吐随之衰减 —— 因为每生成一个 token,都必须把整条 cache 从 HBM 完整读一遍。 下图按 H100 SXM(3.35 TB/s,单序列,理论下界)估算。

五、五个要点

01
Q 不是问题,KV 才是

Q 的显存占用与序列长度无关,decode 时单层仅 64×128×2B = 16 KiB。真正撑爆显存的是那 80 GiB 的 K/V。优化长上下文,本质上是在优化 KV cache。

02
prefill 算力密集,decode 访存密集

prefill 把成千上万个 token 的 Q/K/V 一次性算出来,是漂亮的大 GEMM;decode 每步只有一个 Q 向量,退化成 GEMV,算术强度约 8 FLOP/byte,远低于 H100 约 590 的拐点。

03
多轮对话不重算历史

第 2 轮起,用户新消息只需 prefill 新增的那几百个 token,之前所有 K/V 直接命中缓存。这就是「前缀缓存」,也是同一窗口连续对话比新开窗口快得多的原因。

04
越聊越慢是物理规律

空窗口时每 token 约 12 ms(只需读 20B 激活权重),满窗口时约 38 ms(额外读 80 GiB cache)。吞吐从约 84 tok/s 掉到约 27 tok/s,与模型质量无关。

05
GQA 是这一切的前提

若用 MHA(64 份 KV),256K 的 cache 会是 640 GiB,单机八卡都放不下。GQA 把它压到 80 GiB,同时让每份 KV 被 8 个 Q 头复用,decode 的算术强度也提高 8 倍。

参数取自 HYV3 配置:80 层 / 64 Q 头 / 8 KV 头 / head_dim 128 / bf16 / max_position_embeddings 262144。 性能数字为访存理论下界估算,未计入通信、调度与 kernel 效率损失,仅用于说明量级关系。
