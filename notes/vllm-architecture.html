vLLM 完整调用链路拆解vLLM End-to-End Call Chain

这篇笔记把 vLLM 从 vllm serve 拉起服务、到一条 curl 请求打进来、再到模型前向、采样、流式返回的 完整调用链路 串成一条线,配多张图,帮你理清"vLLM 是怎么跑起来的、为什么快"。基于 V1 引擎(2025 起的默认架构)。This note traces the full call path through vLLM — from vllm serve bringing the service up, through a curl request arriving, the model forward, sampling, and the streamed response — with figures along the way, so that "how vLLM runs and why it is fast" hangs together. Based on the V1 engine, the default architecture since 2025.

一句话总览: vLLM = OpenAI 兼容 API 服务 + 把 CPU 活(分词/调度/流式)和 GPU 活(前向)拆进不同进程 + 连续批处理(continuous batching) + PagedAttention 像操作系统分页一样管理 KV cache。这四点撑起了它"高吞吐"的核心卖点。In one line: vLLM = an OpenAI-compatible API service + CPU work (tokenisation, scheduling, streaming) and GPU work (the forward pass) split into separate processes + continuous batching + PagedAttention managing KV cache the way an OS manages pages. Those four things are what its high-throughput claim rests on.

0 · 为什么需要 vLLM0 · Why vLLM exists

朴素的 LLM 推理有两个致命浪费,vLLM 就是冲着这两点去的:Naive LLM inference wastes resources in two fatal ways, and vLLM targets both:

朴素实现的痛点 What hurts in a naive implementation

  • 显存碎片:给每个请求预留 max_len 的连续 KV cache,实际只用一点点,利用率常常 < 40%。Memory fragmentation: reserving a contiguous max_len of KV cache per request while using only a fraction of it, often leaving utilisation below 40%.
  • 静态批处理:一个 batch 里要等最慢的请求生成完才能整批结束,GPU 大量空转。Static batching: the whole batch waits for its slowest request to finish, leaving the GPU idling for long stretches.

vLLM 的解法 How vLLM answers

  • PagedAttention:KV cache 切成固定大小的 block,按需分配、可共享,显存利用率拉到 > 90%。PagedAttention: KV cache is cut into fixed-size blocks, allocated on demand and shareable, pushing utilisation above 90%.
  • 连续批处理:每一步(每次前向)都能让完成的请求退出、新请求插入,GPU 始终满载。Continuous batching: at every step (every forward) finished requests leave and new ones join, so the GPU stays saturated.

结果:相比朴素 HF Transformers 实现,吞吐量可达 10–24× 量级的提升(取决于模型与负载)。The result: throughput on the order of 10–24× a naive HF Transformers implementation, depending on model and load.

记忆锚点:上半截(进程 A)全是 CPU 活,下半截(进程 B)是 GPU 活。V1 把它们拆成两个进程,就是为了让分词/流式这些 CPU 活和 GPU 前向重叠执行,绕开 Python 的 GIL。这是 V1 相对 V0 最大的架构升级。An anchor for memory: the top half (process A) is all CPU work, the bottom half (process B) is GPU work. V1 splits them into two processes precisely so that CPU work like tokenisation and streaming can overlap with the GPU forward, sidestepping Python's GIL. This is V1's biggest architectural upgrade over V0.

3 · 服务拉起:vllm serve 发生了什么3 · Startup: what vllm serve does

当你敲下 vllm serve Qwen/Qwen2.5-7B-Instruct,这一串事情按顺序发生:When you type vllm serve Qwen/Qwen2.5-7B-Instruct, this happens in order:

  1. 解析参数,起 HTTP 服务Parse arguments, start the HTTP service
    CLI 解析 EngineArgs(模型名、TP 大小、gpu-memory-utilization 等),用 FastAPI + uvicorn 在 :8000 起 OpenAI 兼容服务。The CLI parses EngineArgs (model name, TP size, gpu-memory-utilization and so on) and starts the OpenAI-compatible service on :8000 with FastAPI and uvicorn.
  2. 构建 AsyncLLM,拉起 EngineCore 子进程Build AsyncLLM, spawn the EngineCore subprocess
    AsyncLLM 通过 AsyncMPClient fork/spawn 出独立的 EngineCore 进程,两边用 ZeroMQ 做 IPC。AsyncLLM forks or spawns a separate EngineCore process through AsyncMPClient, with ZeroMQ for IPC between them.
  3. Executor 起 Worker,每张 GPU 一个Executor starts one Worker per GPU
    单机多卡用 MultiProcExecutor,每个 Worker 绑一张 GPU,内含一个 GPUModelRunner。Multi-GPU on one host uses MultiProcExecutor; each Worker binds a GPU and holds a GPUModelRunner.
  4. 加载模型权重Load model weights
    ModelRunner 调 model_loader 把权重读到显存(支持 safetensors / GGUF / bitsandbytes 等),按 TP/PP 切分到各卡。ModelRunner calls model_loader to read weights into GPU memory (safetensors, GGUF, bitsandbytes and more) and shard them across GPUs by TP/PP.
  5. 显存 profiling + 分配 KV cacheMemory profiling + KV cache allocation
    跑一次假的前向探测峰值显存,用 剩余显存 × gpu_memory_utilization 推算能放多少个 KV block,一次性把这块"显存池"占下来。Runs a dummy forward to probe peak memory, works out how many KV blocks fit from remaining memory × gpu_memory_utilization, and claims that memory pool in one go.
  6. 捕获 CUDA Graph(可选但默认开)Capture CUDA Graphs (optional, on by default)
    对常见 batch 形状提前 capture CUDA Graph,消除 decode 阶段的 kernel launch 开销。Captures CUDA Graphs ahead of time for common batch shapes, removing kernel launch overhead during decode.
  7. 就绪,EngineCore 进入 busy loopReady; EngineCore enters its busy loop
    服务打印 Application startup complete,开始空转等请求。The service prints Application startup complete and idles, waiting for requests.
高频考点 —— gpu-memory-utilization:它不是限制权重大小,而是决定"显存里留多大一块给 KV cache 池"。调大 → 能容纳更多并发/更长上下文,但留给临时激活的余量变小,过大可能 OOM。默认 0.9。A frequent point of confusion — gpu-memory-utilization: it does not cap the weight size; it decides how much memory is set aside for the KV cache pool. Raise it → more concurrency and longer contexts, but less headroom for transient activations, and too high will OOM. Default 0.9.

4 · 模型 & KV cache "拉起"的本质4 · What "bringing up the model & KV cache" really means

很多人以为"模型拉起 = 加载权重"。在 vLLM 语境里它其实是两件事,第二件才是重点:People often read "bringing up the model" as "loading weights". In vLLM it is two things, and the second one is the interesting one:

① 加载权重 ① Load the weights

把 N B 参数读进显存,按张量并行(TP)切到各卡。这部分和别的框架差不多。Read N billion parameters into GPU memory, sharded across GPUs by tensor parallelism. This part looks like any other framework.

② 圈定 KV cache 池 ② Stake out the KV cache pool

权重之外的所有剩余显存切成等大 block 预先占住。这是 vLLM 高吞吐的物理基础。All memory left after the weights is carved into equal-sized blocks and claimed up front. This is the physical basis of vLLM's throughput.

关键洞察:第 6–7 步的"逐 token 生成"并不是这一条请求独占 GPU。每一个 decode step,调度器都会把当前所有活跃请求拼成一个大 batch 一起算 —— 这就是连续批处理,下一节细讲。The key insight: the token-by-token generation in steps 6–7 does not give this request the GPU to itself. 6 · 连续批处理(Continuous Batching)6 · Continuous batching

传统静态批处理:一批请求必须同生共死。连续批处理:以 step(一次前向)为粒度动态进出。Traditional static batching ties a batch of requests to a shared fate. Continuous batching lets them enter and leave at the granularity of a step (one forward).

7 · PagedAttention & KV cache:像操作系统分页7 · PagedAttention & KV cache: paging, like an OS

这是 vLLM 的招牌,几乎必考。核心类比一句话:KV cache 之于 vLLM,就像物理内存之于操作系统。This is vLLM's signature idea and comes up constantly. The analogy in one line: KV cache is to vLLM what physical memory is to an operating system.

背景:自回归生成里,每个已生成 token 的 Key/Value 要缓存下来给后续 token 做注意力(避免重算)。这块缓存就是 KV cache,它随序列变长而线性增长,是长序列推理的显存大头。Background: in autoregressive generation the Key/Value of every generated token has to be cached for later tokens to attend to, avoiding recomputation. That cache is the KV cache; it grows linearly with sequence length and dominates memory in long-sequence inference.

PagedAttention 把每个序列的 KV cache 切成固定大小的 block(比如每 block 存 16 个 token 的 KV),逻辑上连续、物理上可以散落 —— 就像 OS 的虚拟内存分页:PagedAttention cuts each sequence's KV cache into fixed-size blocks (say 16 tokens of KV per block) that are logically contiguous but physically scattered — exactly like virtual memory paging in an OS:

这种设计直接带来三个好处:The design buys three things directly:

  • 几乎零碎片:按 block 粒度分配,不再为每个请求预留 max_len 连续空间,显存利用率 > 90%。Almost no fragmentation: allocation happens per block, with no contiguous max_len reserved per request, so utilisation exceeds 90%.
  • KV 共享(prefix caching):多个请求的相同前缀(如同一个 system prompt)可以指向同一批物理块,省显存又省重复 prefill。KV sharing (prefix caching): requests with a common prefix, such as the same system prompt, can point at the same physical blocks, saving both memory and repeated prefill.
  • copy-on-write:beam search / 并行采样分叉时,共享块只在写时才复制。Copy-on-write: when beam search or parallel sampling forks, shared blocks are only copied when written.

8 · 调度器:prefill 与 decode 的统一8 · The scheduler: unifying prefill and decode

V1 调度器做了个漂亮的简化:不再区分 prefill 和 decode 阶段,统一表示成"这一步给每个请求跑几个 token"。The V1 scheduler makes an elegant simplification: it no longer distinguishes prefill from decode, expressing both as "how many tokens each request runs this step".

Prefill 阶段Prefill

处理输入 prompt,一次算很多 token,算力密集(compute-bound)。延迟体现为 首 token 时间 TTFT。Processes the input prompt, many tokens at once, compute-bound. Its latency shows up as time to first token, TTFT.

Decode 阶段Decode

每步只生成 1 token,要反复读全部 KV cache,访存密集(memory-bound)。延迟体现为 每 token 时间 TPOT。One token per step, re-reading the whole KV cache each time, memory-bound. Its latency shows up as time per output token, TPOT.

Chunked Prefill:长 prompt 的 prefill 会一次性吃满 GPU、把正在 decode 的请求"饿死"造成卡顿。解法是把长 prefill 切成小块,和 decode 请求混在同一个 batch 里跑,兼顾吞吐与延迟。这也是统一调度表示带来的红利。Chunked prefill: a long prompt's prefill can saturate the GPU in one go and starve requests that are decoding, causing visible stutter. The fix is to cut long prefills into chunks and run them in the same batch as decode requests, serving throughput and latency together. This too is a dividend of the unified scheduling representation.

9 · 为什么拆成多进程(V1 的核心升级)9 · Why split into multiple processes (V1's core upgrade)

好处:GPU 进程永远不会因为"主线程在忙着分词/拼 JSON"而空等。CPU 活和 GPU 活真正并行,这是 V1 把吞吐进一步拉高的关键。代价是引入了 IPC 复杂度,V1 用"只传增量 + worker 缓存状态"把这个开销压到很低。The payoff: the GPU process never idles because the main thread is busy tokenising or assembling JSON. CPU work and GPU work run genuinely in parallel, which is how V1 pushes throughput higher still. The cost is IPC complexity, which V1 keeps cheap by sending only deltas and caching state on the worker.
