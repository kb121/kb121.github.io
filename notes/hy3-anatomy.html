只用两个元数据文件,拆解一个 300B MoEReverse-Engineering a 300B MoE from Two Metadata Files

对象是 tencent/Hy3 (架构名 HYV3ForCausalLM)。手上只有 config.json 和 model.safetensors.index.json 两个文件,一个权重字节都没下载。这篇记录怎么只凭这两份元数据,把结构还原到字节级对得上账 —— 并且在对账差出来的 30,720 个字节里,读出一个不写在 config 里的实现细节。 最后落到真正要命的问题:这东西到底跑不跑得起来。

同一份 config 我之前从并行切分的角度写过一篇 TP=4 / PP=4 / EP=4,那篇关心的是「切完之后每张卡装什么」; 这篇关心的是「这份 checkpoint 里到底有什么」。两篇可以对着看。

一、起点:两个文件,零权重

config.json 给出维度,index.json 给出每个张量叫什么、在第几个分片、以及总字节数。 两者交叉验证,足够把结构完全钉死。先看 config 里的关键项:

二、先把总账算平

按维度逐项推:注意力四个投影、dense 层 FFN、每层 192 个专家加 1 个共享专家、路由、各种 norm、 词嵌入与 lm_head(tie_word_embeddings 为 false,两者各算一份)。

79 个 MoE 层吃掉了 98.3% 的参数。注意力在整个模型里只占约 2%, 这正是 MoE 的形状:参数几乎全在专家里,计算却大部分不在。

三、剩下的 30,720 字节是谁

推算结果是 298,786,155,776 个参数。按 bf16 每个 2 字节算,应该是 597,572,311,552 字节。而 index 里声明的 total_size 是 597,572,342,272 —— 多出 30,720 字节。

0.000005% 的偏差,大到不可能是舍入,小到不可能是漏了一层。换算成参数是 15,360 个, 而 15360 = 80 × 192 —— 恰好是 80 个 MoE 层各自那 192 个 expert_bias 的总数。 也就是说这些值每个多占了 2 字节: 

参数总数        298,786,155,776
全部按 bf16     × 2      = 597,572,311,552
expert_bias 改 fp32  + 15,360 × 2  =      30,720
                        ------------------------
                         597,572,342,272   ← 与 index 声明完全相等

结论:整个模型是 bf16,唯独 expert_bias 存成 fp32。 这件事 config 里一个字都没写,只能从字节数反推出来。

而它是有道理的。这个 bias 是无辅助损失负载均衡里的调节量 —— 每步根据专家的负载偏差加减一个很小的增量。 bf16 只有 8 位尾数,在数值已经长到一定量级后,小增量会被直接舍入掉,均衡机制就悄悄失效了。 用 fp32 存这 15,360 个数,代价是 30 KB,换来的是负载均衡不会随训练进程失灵。

四、81 层里藏着一个 MTP

index 里的层号是 0 到 80,共 81 个,但 config 写的是 80 层。多出来的那层不是笔误 —— 第 80 层带着 eh_proj、enorm、hnorm、final_layernorm 这几个主干层没有的张量, 这是 MTP(多 token 预测)模块,对应 config 里的 num_nextn_predict_layers: 1。

动图 2:81 层的构成(鼠标划过看细节)
层 0 · dense FFN 层 1–79 · MoE 层 80 · MTP 模块
MTP 模块自带完整的注意力和 192 个专家,本身就有 3.75 B 参数。 它在训练时提供额外的预测信号,在推理时可以拿来做投机解码 —— 但如果不用,这 7.5 GB 权重是可以不加载的。 顺带说明:按 config 的 80 层直接推,会得到 295.03 B,那是不含这一层的数; checkpoint 里实际躺着的是 298.79 B。

五、14.5 倍稀疏:97.8% 的张量都是专家

47,138 个张量条目里,46,080 个是专家权重。这个比例本身就说明了 MoE 的工程形态: 绝大多数张量在绝大多数时候是不参与计算的,但它们必须全部常驻显存。

有个耐人寻味的设计巧合:激活的 FFN 宽度几乎等于 dense 层宽度 —— 9 个专家(8 路由 + 1 共享)× 1536 = 13,824,而第 0 层 dense 是 13,312。 专家切得很细(单个只有 dense FFN 的 11.5%),但每 token 实际算的 FFN 规模和一个 dense 层基本对齐。

六、谱系:别人的路由,自己的注意力

路由这一侧几乎是照着 DeepSeek-V3 那套走的:sigmoid 打分(moe_router_use_sigmoid)、 用 expert bias 做无辅助损失均衡、首层 dense、共享专家、MTP。连 router_scaling_factor: 2.826 这种带小数的缩放系数都是同一路数。

但注意力完全分岔了:不是 MLA,而是 GQA 64/8,外加 qk_norm。 也就是说它放弃了 MLA 那条压缩 KV 的路线,直接用分组共享把 KV 压到八分之一,再靠 q/k 上的 RMSNorm 稳住训练。

还有一处不常见:num_heads × head_dim = 64 × 128 = 8192,是 hidden_size 4096 的两倍。 多数模型这两个数相等,这里 q_proj 是一个 4096 → 8192 的扩张投影,注意力被单独加宽而残差流保持窄。 这个细节在做张量并行时会直接坑到 shape,我在 并行那篇里单开了一节讲,这里不重复。

七、真正卡脖子的是显存

前面都是结构,这一节是能不能上线的问题。权重 bf16 要 556.5 GiB, 而满 256K 上下文的 KV cache 还要 80 GiB。 把两者放进同一个显存池里看:

只算权重与 KV,未计激活、通信缓冲与框架 workspace,所以这是个乐观上界 —— 真实可用容量还要再打折。H100 按 80 GB 计。

结论比较硬:8 卡 H100 在 bf16 下连一条满上下文请求都服务不了。 权重装完只剩约 39.5 GiB,而一条 256K 序列的 KV 就要 80 GiB —— 缺口整整一倍。 实际可行的路径无非三条:把权重量化到 FP8(立刻腾出约 318 GiB)、扩到 16 卡以上、 或者用 KV 池化把 cache 卸到 GPU 之外。

这里算的是整池够不够,把所有卡的显存当成一个整体。真正部署时还要看切完之后 每张卡各自装什么 —— 那是另一码事,在 TP / PP / EP 那篇里按 16 卡布局算过:单卡 34.7 GiB 权重、20 KiB/token 的 KV。

八、两个看着像遗留项的开关

output_router_logits: true —— 这通常是训练时算辅助损失用的。推理配置里开着, 会让每层都多吐一路 router logits,白白占带宽。不过这个模型用的是无辅助损失的 bias 均衡, 所以它更可能是留给负载监控或调试的。

use_grouped_mm: false —— 192 个细粒度专家却没开 grouped GEMM, 意味着 MoE 那段大概率在走逐专家的循环。每个专家只有 1536 的中间维度,单独发 kernel 的话 GPU 基本吃不饱,这正是 grouped GEMM 最典型的用武之地。

另外 rope_theta = 11158840.0 是个很不圆整的数,不像手设的 1e7, 更像是按 256K 的目标长度反解出来的。

九、要点

01
元数据足够还原结构

不下载一个权重字节,只靠维度和 total_size 交叉验证,就能把 300B 模型的结构钉到字节级对得上。审模型、估显存、排查加载问题,都不必先拉 600 GB。

02
对不上的那一点最有价值

30,720 字节的差值反推出 expert_bias 用 fp32 存 —— 这是 config 里没写、只能从字节数看出来的实现选择,背后是均衡机制怕被 bf16 舍入吃掉。

03
层数会骗人

config 写 80 层,权重里有 81 个层号。多出来的是 MTP 模块,自带注意力和全套专家、独占 3.75 B 参数。按 config 分配显存会直接少算 7.5 GB。

04
稀疏省的是算力,不是显存

每 token 只激活 6.9% 的参数,但 97.8% 的张量必须常驻。MoE 换来的是算力效率,显存账单一分没少 —— 这决定了它的部署形态。

05
先算显存,再谈优化

8×H100 bf16 装完权重只剩 39.5 GiB,而一条满窗口 KV 要 80 GiB。在这个前提没解决之前,谈 kernel 调优是没有意义的。

06
混合谱系已是常态

路由抄 DeepSeek 的成熟方案(sigmoid + bias 均衡 + 共享专家 + MTP),注意力却选了 GQA 而非 MLA。现在的模型不再有单一血统,读配置时要分模块看。

全部结论仅由 config.json 与 model.safetensors.index.json 推导,未加载任何权重。 参数量为按维度独立推算后与 index 声明的 total_size 对账所得。 显存部分按 H100 80 GB 计,只算权重与 KV,未计激活与框架 workspace,属乐观上界。
