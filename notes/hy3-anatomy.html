混元3模型结构分析Hunyuan 3 Model Architecture Analysis

分析对象是腾讯混元团队的 Hy3,模型卡 tencent/Hy3, 架构名 HYV3ForCausalLM,Apache-2.0。 全文结论只来自模型卡上的两个元数据文件: config.json 给出各处维度, model.safetensors.index.json 给出每个张量的名字、所在分片和总字节数。两者交叉验证足以把结构钉死,没有下载任何权重。The subject is Tencent Hunyuan's Hy3, model card tencent/Hy3, architecture HYV3ForCausalLM, Apache-2.0. Every conclusion here comes from just two metadata files on that card: config.json for the dimensions, and model.safetensors.index.json for every tensor's name, shard and the total byte count. Cross-checking the two pins the structure down completely, with no weights downloaded.

模型卡自己也列了一张规格表,所以这篇有个现成的对照组:先只看这两个文件推算,再回头和官方数字比。 结果是全部对上,而且推算还能补出规格表没写的东西 —— 比如权重实际是怎么存的。The model card also publishes a spec table, so this note has a ready-made control group: derive everything from the two files first, then compare against the official numbers. They all match — and the derivation additionally recovers something the spec table omits, namely how the weights are actually stored.

79 个 MoE 层吃掉了 98.3% 的参数。注意力在整个模型里只占约 2%, 这正是 MoE 的形状:参数几乎全在专家里,计算却大部分不在。The 79 MoE layers consume 98.3% of the parameters. Attention is only about 2% of the whole model — which is exactly the shape of MoE: nearly all the parameters live in the experts, and most of the computation does not.

三、剩下的 30,720 字节是谁3 · Who the remaining 30,720 bytes belong to

推算结果是 298,786,155,776 个参数。按 bf16 每个 2 字节算,应该是 597,572,311,552 字节。而 index 里声明的 total_size 是 597,572,342,272 —— 多出 30,720 字节。The derivation gives 298,786,155,776 parameters. At 2 bytes each in bf16 that should be 597,572,311,552 bytes. The total_size declared in the index is 597,572,342,272 — 30,720 bytes more.

0.000005% 的偏差,大到不可能是舍入,小到不可能是漏了一层。换算成参数是 15,360 个, 而 15360 = 80 × 192 —— 恰好是 80 个 MoE 层各自那 192 个 expert_bias 的总数。 也就是说这些值每个多占了 2 字节:A 0.000005% discrepancy: too large to be rounding, too small to be a missing layer. In parameters that is 15,360, and 15360 = 80 × 192 — exactly the total number of expert_bias values across 80 MoE layers, 192 each. In other words each of them takes 2 bytes more:

参数总数        298,786,155,776
全部按 bf16     × 2      = 597,572,311,552
expert_bias 改 fp32  + 15,360 × 2  =      30,720
                        ------------------------
                         597,572,342,272   ← 与 index 声明完全相等parameter count      298,786,155,776
all in bf16          × 2      = 597,572,311,552
expert_bias in fp32  + 15,360 × 2  =      30,720
                        ------------------------
                         597,572,342,272   ← exactly the index's declared size

结论:整个模型是 bf16,唯独 expert_bias 存成 fp32。 这件事 config 里一个字都没写,只能从字节数反推出来。Conclusion: the whole model is bf16, except expert_bias, which is stored as fp32. The config says nothing at all about this; it can only be inferred from the byte count.

而它是有道理的。这个 bias 是无辅助损失负载均衡里的调节量 —— 每步根据专家的负载偏差加减一个很小的增量。 bf16 只有 8 位尾数,在数值已经长到一定量级后,小增量会被直接舍入掉,均衡机制就悄悄失效了。 用 fp32 存这 15,360 个数,代价是 30 KB,换来的是负载均衡不会随训练进程失灵。And there is a reason for it. That bias is the adjustment term in auxiliary-loss-free load balancing — a small increment added or subtracted each step according to how far an expert's load has drifted. bf16 has only 8 mantissa bits, so once the value has grown to a certain magnitude the small increment is rounded straight away and the balancing mechanism quietly stops working. Storing those 15,360 numbers in fp32 costs 30 KB and buys balancing that does not fail as training progresses.

四、81 层里藏着一个 MTP4 · An MTP hidden among the 81 layers

index 里的层号是 0 到 80,共 81 个,但 config 写的是 80 层。多出来的那层不是笔误 —— 第 80 层带着 eh_proj、enorm、hnorm、final_layernorm 这几个主干层没有的张量, 这是 MTP(多 token 预测)模块,对应 config 里的 num_nextn_predict_layers: 1。The index numbers layers 0 through 80, 81 in all, while the config says 80. The extra one is not a typo — layer 80 carries eh_proj, enorm, hnorm and final_layernorm, tensors no backbone layer has. This is the MTP (multi-token prediction) module, corresponding to num_nextn_predict_layers: 1 in the config.

MTP 模块自带完整的注意力和 192 个专家,本身就有 3.75 B 参数 —— 模型卡把它单独列为 3.8 B,对得上。这也解释了那张规格表为什么写「总参数 295B」却又单列一行 MTP: 295 B 是不含它的数,磁盘上实际躺着 295 + 3.8 = 298.79 B。 按 num_hidden_layers: 80 去分配显存,就会少算这 7.5 GB。 它也不是可选摆设 —— 官方的 vLLM 与 SGLang 启动脚本都默认开着它做投机解码。The MTP module brings its own full attention and 192 experts, and is 3.75 B parameters by itself — the model card lists it separately as 3.8 B, which matches. It also explains why the spec table says "295B total" and then adds a separate MTP row: 295 B excludes it, and what is actually on disk is 295 + 3.8 = 298.79 B. Budget memory from num_hidden_layers: 80 and you will be 7.5 GB short. Nor is it optional decoration — the official vLLM and SGLang launch scripts enable it by default for speculative decoding.

五、14.5 倍稀疏:97.8% 的张量都是专家5 · 14.5× sparsity: 97.8% of tensors are experts

47,138 个张量条目里,46,080 个是专家权重。这个比例本身就说明了 MoE 的工程形态: 绝大多数张量在绝大多数时候是不参与计算的,但它们必须全部常驻显存。Of 47,138 tensor entries, 46,080 are expert weights. That ratio alone describes the engineering shape of MoE: the vast majority of tensors are not participating in the computation most of the time, yet all of them must stay resident in memory.

有个耐人寻味的设计巧合:激活的 FFN 宽度几乎等于 dense 层宽度 —— 9 个专家(8 路由 + 1 共享)× 1536 = 13,824,而第 0 层 dense 是 13,312。 专家切得很细(单个只有 dense FFN 的 11.5%),但每 token 实际算的 FFN 规模和一个 dense 层基本对齐。There is an intriguing coincidence in the design: the active FFN width almost equals the dense layer's width — 9 experts (8 routed + 1 shared) × 1536 = 13,824, while layer 0's dense FFN is 13,312. The experts are sliced very finely (one is just 11.5% of the dense FFN), yet the FFN each token actually computes is about the size of one dense layer.

六、谱系:别人的路由,自己的注意力6 · Lineage: someone else's routing, its own attention

路由这一侧几乎是照着 DeepSeek-V3 那套走的:sigmoid 打分(moe_router_use_sigmoid)、 用 expert bias 做无辅助损失均衡、首层 dense、共享专家、MTP。连 router_scaling_factor: 2.826 这种带小数的缩放系数都是同一路数。The routing side follows DeepSeek-V3 almost exactly: sigmoid scoring (moe_router_use_sigmoid), auxiliary-loss-free balancing through an expert bias, a dense first layer, a shared expert, MTP. Even a fractional scaling constant like router_scaling_factor: 2.826 is from the same playbook.

但注意力完全分岔了:不是 MLA,而是 GQA 64/8,外加 qk_norm。 也就是说它放弃了 MLA 那条压缩 KV 的路线,直接用分组共享把 KV 压到八分之一,再靠 q/k 上的 RMSNorm 稳住训练。But attention diverges completely: not MLA, but GQA 64/8 with qk_norm. It abandons MLA's route of compressing KV, using grouped sharing to cut KV to an eighth instead, and stabilising training with RMSNorm on q and k.

还有一处不常见:num_heads × head_dim = 64 × 128 = 8192,是 hidden_size 4096 的两倍。 多数模型这两个数相等,这里 q_proj 是一个 4096 → 8192 的扩张投影,注意力被单独加宽而残差流保持窄。 这个细节在做张量并行时会直接坑到 shape,我在 并行那篇里单开了一节讲,这里不重复。One more uncommon detail: num_heads × head_dim = 64 × 128 = 8192, twice the hidden_size of 4096. In most models those two are equal; here q_proj is an expanding 4096 → 8192 projection, widening attention while the residual stream stays narrow. This detail bites shapes directly during tensor parallelism, and I gave it its own section in the parallelism note, so I will not repeat it here.

结论比较硬:8 卡 H100 在 bf16 下连一条满上下文请求都服务不了。 权重装完只剩约 39.5 GiB,而一条 256K 序列的 KV 就要 80 GiB —— 缺口整整一倍。 这一点在模型卡上得到了印证。官方部署建议原文是:「Hy3 共 295B 参数,若要用 8 卡部署, 我们推荐 H20-3e 或其他显存容量更大的卡。」H20-3e 是 141 GB 版本,8 张合计 1050 GiB, 装完权重还剩约 494 GiB —— 够放 6 条满窗口序列。不是官方不推荐 H100,是 80 GB 这个容量根本放不下。 在上图把卡型切到 H20-3e 就能看到这个差别。The conclusion is blunt: 8×H100 in bf16 cannot serve even one full-context request. After the weights there is about 39.5 GiB left, and one 256K sequence's KV needs 80 GiB — short by a full factor of two. The model card confirms this. The official deployment note reads: "Hy3 has 295B parameters in total; for an 8-GPU deployment we recommend H20-3e or another card with larger memory capacity." H20-3e is the 141 GB version; eight of them total 1050 GiB, leaving about 494 GiB after the weights — enough for 6 full-window sequences. It is not that they advise against H100; 80 GB simply does not fit. Switch the GPU to H20-3e in the figure above to see the difference.

其余可行路径:扩到 16 卡以上、把权重量化到 FP8(模型卡标注的支持精度只有 BF16,量化要自己做, 官方给了 AngelSlim 工具链)、 或者用 KV 池化把 cache 卸到 GPU 之外。Other viable routes: scale past 16 GPUs, quantise the weights to FP8 (the card lists BF16 as the only supported precision, so you would quantise yourself — they provide the AngelSlim toolchain), or use KV pooling to offload the cache off-GPU.

这里算的是整池够不够,把所有卡的显存当成一个整体。真正部署时还要看切完之后 每张卡各自装什么 —— 那是另一码事,在 TP / PP / EP 那篇里按 16 卡布局算过:单卡 34.7 GiB 权重、20 KiB/token 的 KV。What is computed here is whether the pool as a whole suffices, treating all GPUs' memory as one aggregate. A real deployment also has to consider what each individual GPU holds after sharding — a separate matter, worked out for a 16-GPU layout in the TP / PP / EP note: 34.7 GiB of weights per GPU and 20 KiB of KV per token.

八、两个看着像遗留项的开关8 · Two switches that look like leftovers

output_router_logits: true —— 这通常是训练时算辅助损失用的。推理配置里开着, 会让每层都多吐一路 router logits,白白占带宽。不过这个模型用的是无辅助损失的 bias 均衡, 所以它更可能是留给负载监控或调试的。output_router_logits: true — normally this is for computing an auxiliary loss during training. Left on in an inference config it makes every layer emit an extra stream of router logits, wasting bandwidth. But this model uses auxiliary-loss-free bias balancing, so it is more likely there for load monitoring or debugging.

use_grouped_mm: false —— 192 个细粒度专家却没开 grouped GEMM, 意味着 MoE 那段大概率在走逐专家的循环。每个专家只有 1536 的中间维度,单独发 kernel 的话 GPU 基本吃不饱,这正是 grouped GEMM 最典型的用武之地。use_grouped_mm: false — 192 fine-grained experts with grouped GEMM off suggests the MoE section is most likely running a per-expert loop. With only 1536 of intermediate dimension per expert, launching a separate kernel each leaves the GPU largely idle, which is the textbook case for grouped GEMM.

另外 rope_theta = 11158840.0 是个很不圆整的数,不像手设的 1e7, 更像是按 256K 的目标长度反解出来的。Also rope_theta = 11158840.0 is a distinctly un-round number, not a hand-set 1e7; it looks solved backwards from a 256K target length.

九、要点9 · Takeaways

01
元数据足够还原结构Metadata is enough to reconstruct the structure

不下载一个权重字节,只靠维度和 total_size 交叉验证,就能独立复现模型卡上的 295 B / 3.8 B / 21 B 三个数字,还能补出规格表没写的存储格式。审模型、估显存、排查加载问题,都不必先拉 600 GB。Without downloading a single byte of weights, cross-checking dimensions against total_size independently reproduces the model card's 295 B / 3.8 B / 21 B and additionally recovers a storage format the spec table omits. Auditing a model, estimating memory or debugging a load does not require pulling 600 GB first.

02
对不上的那一点最有价值The part that does not add up is the most valuable

30,720 字节的差值反推出 expert_bias 用 fp32 存 —— 这是 config 里没写、只能从字节数看出来的实现选择,背后是均衡机制怕被 bf16 舍入吃掉。A 30,720-byte gap reveals that expert_bias is stored in fp32 — an implementation choice absent from the config and visible only in the byte count, made because the balancing mechanism would otherwise be eaten by bf16 rounding.

03
层数和参数量都要看口径Layer counts and parameter counts both depend on the convention

num_hidden_layers 是 80,权重里却有 81 个层号;「总参数 295B」也不含那一层。MTP 自带注意力和全套专家、独占 3.75 B。照 config 分配显存会少算 7.5 GB。num_hidden_layers is 80, yet the weights carry 81 layer indices; "295B total" also excludes that layer. MTP brings its own attention and a full set of experts, 3.75 B on its own. Budget memory from the config and you are 7.5 GB short.

04
稀疏省的是算力,不是显存Sparsity saves compute, not memory

每 token 只激活 6.9% 的参数,但 97.8% 的张量必须常驻。MoE 换来的是算力效率,显存账单一分没少 —— 这决定了它的部署形态。Only 6.9% of parameters activate per token, yet 97.8% of tensors must stay resident. What MoE buys is compute efficiency; the memory bill is undiminished — and that dictates how it can be deployed.

05
先算显存,再谈优化Do the memory arithmetic before discussing optimisation

8×H100 bf16 装完权重只剩 39.5 GiB,而一条满窗口 KV 要 80 GiB。在这个前提没解决之前,谈 kernel 调优是没有意义的。8×H100 in bf16 leaves 39.5 GiB after the weights, while one full-window KV needs 80 GiB. Until that is resolved, kernel tuning is beside the point.

06
混合谱系已是常态Mixed lineage is now the norm

路由抄 DeepSeek 的成熟方案(sigmoid + bias 均衡 + 共享专家 + MTP),注意力却选了 GQA 而非 MLA。现在的模型不再有单一血统,读配置时要分模块看。The routing borrows DeepSeek's proven recipe (sigmoid + bias balancing + shared expert + MTP), while attention chose GQA over MLA. Models no longer have a single bloodline; read the config module by module.
