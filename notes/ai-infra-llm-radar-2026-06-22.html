结论:历史上“如何训练更大模型”是主线;现在“如何把长上下文、多轮 Agent、开源权重和昂贵算力稳定服务出去”成为主线。

历史:从模型训练优化到推理服务优化

早期 AI Infra 的核心矛盾是训练阶段的显存和通信,代表是 DeepSpeed/ZeRO 这类分布式优化库。2023 年后,开源大模型开始从“可训练”转向“可服务”:vLLM 用 PagedAttention 解决 KV cache 碎片化,llama.cpp 把本地推理变成开发者日常工具。这个阶段的评价指标主要是 tokens/s、显存占用、batching 和硬件覆盖。

当下:推理引擎、KV cache、Agent runtime 同时收敛

2026 年 7 月的证据很集中:vLLM 0.26.0 把 Inkling、DeepSeek-V4、per-KV-group attention backend、KV offloading、MoE router GEMM、FlashInfer/NIXL 依赖放在同一条 release 主线;SGLang 0.5.16 在 574 PRs 中同时推进 DSpark、Inkling、UnifiedRadixTree,并删除实验性量化路径,把 NVFP4 GEMM 收敛到 FlashInfer;FlashInfer 0.6.15 则把 MoE Expert Parallelism、VSA、B300 MLA decode、KDA decode、all-reduce fusion 下沉到 kernel substrate。这说明 serving engine 已经从“单点 kernel 优化”进入“调度器 + kernel substrate + 硬件量化格式 + 模型结构”的协同优化。

另一个当下变化是 KV cache 的身份变化。LMCache v0.5.2 为 vLLM 0.26.0 兼容而发布,并把 CacheBlend、HMA、L2 storage backend 写进 release;ROCm AIC 把 LMCache、NIXL、hipFile/AIS 和 RDMA storage 组成 AMD 侧远端 KV tier;llm-d 的 FS backend 则把 KV blocks 放入共享文件系统,并报告长 prompt 单请求最高 16.8x TTFT speedup。也就是说,KV cache 不再只是 GPU 内存管理细节,而是新的“推理数据平面”。

动态图 4:生产推理路径从无状态变成有状态
过去:request 进来,模型算完就结束。现在:request、prefix、tool call、cache hit、storage tier 都影响下一步调度。

未来:四个判断

  1. KV cache 会产品化。 未来的推理平台会像今天的数据库一样管理 KV:容量、命中率、冷热分层、权限、持久化、跨副本一致性和成本都要被暴露。
  2. 推理引擎会继续“内核共享、调度分化”。 FlashInfer 这类 kernel substrate 会被多个 engine 复用;差异化会体现在 scheduler、prefix/tree cache、speculative policy、observability 和硬件拓扑适配。
  3. Agent Infra 会压迫 serving API。 MCP、LangGraph、LiteLLM、coding agents 的快速 release 意味着请求不再是单轮 chat completion,而是长链路、多工具、多状态、可回放、带凭证委托的 workflow。
  4. 指标会从平均 tokens/s 转向 p99 TTFT、cache hit value、每任务成本和每瓦 tokens。 长上下文 Agent 的用户体验受尾延迟和重复 prefill 支配;数据中心侧的约束也从“有没有 GPU”扩展到“有没有电、有没有融资、有没有可持续利用率”。

未来不是单点“更快 GPU”的故事,而是模型开放性、serving runtime、KV 数据平面、数据中心电力/融资形成闭环:每一层都会反向决定上一层的可用模型、上下文长度和服务形态。
