历史:从模型训练优化到推理服务优化

早期 AI Infra 的核心矛盾是训练阶段的显存和通信,代表是 DeepSpeed/ZeRO 这类分布式优化库。2023 年后,开源大模型开始从“可训练”转向“可服务”:vLLM 用 PagedAttention 解决 KV cache 碎片化,llama.cpp 把本地推理变成开发者日常工具。到 2025-2026 年,OpenAI gpt-oss、DeepSeek、Kimi K3 这类 open-weight / open-frontier 模型把评价指标从“能跑”推到“能长期、低成本、带工具、长上下文地服务”。证据是 gpt-oss 的 Apache 2.0、MoE、MXFP4、128k context 和单 80GB GPU/16GB 部署目标,以及 Kimi K3 的 2.8T MoE、1M context、KDA 与 day-0 serving recipe。

当下:推理引擎、KV cache、Agent runtime 同时收敛

2026 年 8 月 5 日附近的证据很集中:vLLM 0.26.0 把 Inkling、DeepSeek-V4、flexible attention backend、KV offloading/tiered secondary storage 和 streaming parser engine 放在同一条 release 主线;PR #51116 又暴露出 tiered KV offload 需要处理 Linux 发行版内核差异;FlashInfer 0.6.16/0.6.17rc1/nightly 则围绕 SM107、FP4 autotuner、JIT cache、MoE routing 修复快速迭代。这说明 serving engine 已经从“单点 kernel 优化”进入“调度器 + kernel substrate + 硬件量化格式 + 模型 parser + OS 兼容性”的协同优化。

另一个当下变化是 KV cache 的身份变化。LMCache v0.5.2、vLLM tiered storage、llm-d filesystem KV offload 都把 KV 从进程内缓存推进到跨副本、跨存储层、可安装升级的系统组件。Kimi K3 和 DeepSeek-V4-Flash 进一步放大这个问题:2.8T MoE、1M context、KDA、DSpark 和 FP4/FP8 KV 如果没有 prefix/KV 管理,模型开放并不等于低成本可服务。也就是说,KV cache 不再只是 GPU 内存管理细节,而是新的“推理数据平面”。

未来:五个判断

  1. KV cache 会产品化。 未来的推理平台会像今天的数据库一样管理 KV:容量、命中率、冷热分层、权限、持久化、跨副本一致性和成本都要被暴露。证据是 LMCache v0.5.2、vLLM native tiered offload、llm-d FS offload 与 PR #51116 的内核兼容性修复同时出现。
  2. 推理引擎会继续“内核共享、调度分化”。 FlashInfer 这类 kernel substrate 会被多个 engine 复用;差异化会体现在 scheduler、prefix/tree cache、speculative policy、observability、parser、OS 兼容性和硬件拓扑适配。
  3. Agent Infra 会压迫 serving API。 MCP 2026-07-28 的 stateless core、LiteLLM MCP OAuth/resource indicators、LangGraph event projections 都说明请求不再是单轮 chat completion,而是长链路、多工具、多状态、可回放、带凭证委托的 workflow。
  4. 开放模型会把“部署 recipe”变成发布物的一部分。 Kimi K3 的 day-0 vLLM 支持、DSpark draft、MXFP4/KDA/长上下文指南说明,未来模型发布若没有 serving recipe,社区很难把权重转成可用吞吐。
  5. 指标会从平均 tokens/s 转向 p99 TTFT、cache hit value、每任务成本和每瓦 tokens。 长上下文 Agent 的用户体验受尾延迟和重复 prefill 支配;数据中心侧的约束也从“有没有 GPU”扩展到“有没有电、有没有融资、有没有可持续利用率”。
