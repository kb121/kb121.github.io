历史:从模型训练优化到推理服务优化Past: from training optimisation to serving optimisation

早期 AI Infra 的核心矛盾是训练阶段的显存和通信,代表是 DeepSpeed/ZeRO 这类分布式优化库。2023 年后,开源大模型开始从“可训练”转向“可服务”:vLLM 用 PagedAttention 解决 KV cache 碎片化,llama.cpp 把本地推理变成开发者日常工具。到 2025-2026 年,OpenAI gpt-oss、DeepSeek、Kimi K3 这类 open-weight / open-frontier 模型把评价指标从“能跑”推到“能长期、低成本、带工具、长上下文地服务”。证据是 gpt-oss 的 Apache 2.0、MoE、MXFP4、128k context 和单 80GB GPU/16GB 部署目标,以及 Kimi K3 的 2.8T MoE、1M context、KDA 与 day-0 serving recipe。Early AI infra was dominated by training-side memory and communication, exemplified by distributed libraries like DeepSpeed/ZeRO. After 2023 open models shifted from "trainable" to "servable": vLLM solved KV cache fragmentation with PagedAttention, and llama.cpp made local inference an everyday developer tool. By 2025-2026, open-weight and open-frontier models such as OpenAI gpt-oss, DeepSeek and Kimi K3 moved the yardstick from "it runs" to "it serves long context with tools, cheaply, over time." The evidence: gpt-oss shipping Apache 2.0, MoE, MXFP4, 128k context and single-80GB-GPU / 16GB deployment targets, and Kimi K3 shipping a 2.8T MoE, 1M context, KDA and a day-0 serving recipe.

当下:推理引擎、KV cache、Agent runtime 同时收敛Present: inference engines, KV cache and agent runtimes converging at once

2026 年 8 月 5 日附近的证据很集中:vLLM 0.26.0 把 Inkling、DeepSeek-V4、flexible attention backend、KV offloading/tiered secondary storage 和 streaming parser engine 放在同一条 release 主线;PR #51116 又暴露出 tiered KV offload 需要处理 Linux 发行版内核差异;FlashInfer 0.6.16/0.6.17rc1/nightly 则围绕 SM107、FP4 autotuner、JIT cache、MoE routing 修复快速迭代。这说明 serving engine 已经从“单点 kernel 优化”进入“调度器 + kernel substrate + 硬件量化格式 + 模型 parser + OS 兼容性”的协同优化。The evidence around 5 August 2026 is unusually concentrated. vLLM 0.26.0 puts Inkling, DeepSeek-V4, a flexible attention backend, KV offloading / tiered secondary storage and a streaming parser engine on one release line; PR #51116 then exposes that tiered KV offload has to cope with kernel differences across Linux distributions; FlashInfer 0.6.16 / 0.6.17rc1 / nightly iterate rapidly on SM107, the FP4 autotuner, JIT cache and MoE routing. Serving engines have moved past single-point kernel optimisation into co-optimising scheduler, kernel substrate, hardware quantisation format, model parser and OS compatibility.

另一个当下变化是 KV cache 的身份变化。LMCache v0.5.2、vLLM tiered storage、llm-d filesystem KV offload 都把 KV 从进程内缓存推进到跨副本、跨存储层、可安装升级的系统组件。Kimi K3 和 DeepSeek-V4-Flash 进一步放大这个问题:2.8T MoE、1M context、KDA、DSpark 和 FP4/FP8 KV 如果没有 prefix/KV 管理,模型开放并不等于低成本可服务。也就是说,KV cache 不再只是 GPU 内存管理细节,而是新的“推理数据平面”。The other shift is what KV cache is. LMCache v0.5.2, vLLM tiered storage and llm-d filesystem KV offload all push KV from an in-process cache to a cross-replica, cross-tier, installable and upgradable system component. Kimi K3 and DeepSeek-V4-Flash amplify this: with a 2.8T MoE, 1M context, KDA, DSpark and FP4/FP8 KV, opening the weights does not make the model cheap to serve unless prefix and KV management come with it. KV cache is no longer a GPU memory-management detail — it is the new inference data plane.

未来:五个判断Future: five calls

  1. KV cache 会产品化。 未来的推理平台会像今天的数据库一样管理 KV:容量、命中率、冷热分层、权限、持久化、跨副本一致性和成本都要被暴露。证据是 LMCache v0.5.2、vLLM native tiered offload、llm-d FS offload 与 PR #51116 的内核兼容性修复同时出现。KV cache will be productised. Inference platforms will manage KV the way databases are managed today: capacity, hit rate, hot/cold tiering, permissions, persistence, cross-replica consistency and cost all surfaced. The evidence is LMCache v0.5.2, vLLM native tiered offload, llm-d FS offload and the kernel-compatibility fix in PR #51116 all appearing at once.
  2. 推理引擎会继续“内核共享、调度分化”。 FlashInfer 这类 kernel substrate 会被多个 engine 复用;差异化会体现在 scheduler、prefix/tree cache、speculative policy、observability、parser、OS 兼容性和硬件拓扑适配。Inference engines will keep sharing kernels while diverging on scheduling. Kernel substrates like FlashInfer get reused across engines; differentiation shows up in the scheduler, prefix/tree cache, speculative policy, observability, parsers, OS compatibility and hardware topology adaptation.
  3. Agent Infra 会压迫 serving API。 MCP 2026-07-28 的 stateless core、LiteLLM MCP OAuth/resource indicators、LangGraph event projections 都说明请求不再是单轮 chat completion,而是长链路、多工具、多状态、可回放、带凭证委托的 workflow。Agent infra will squeeze the serving API. MCP's 2026-07-28 stateless core, LiteLLM's MCP OAuth and resource indicators, and LangGraph event projections all say the same thing: a request is no longer a single-turn chat completion but a long, multi-tool, multi-state, replayable workflow carrying delegated credentials.
  4. 开放模型会把“部署 recipe”变成发布物的一部分。 Kimi K3 的 day-0 vLLM 支持、DSpark draft、MXFP4/KDA/长上下文指南说明,未来模型发布若没有 serving recipe,社区很难把权重转成可用吞吐。Open models will make the deployment recipe part of the release. Kimi K3's day-0 vLLM support, DSpark draft model and MXFP4/KDA/long-context guides suggest that a future release without a serving recipe will leave the community unable to turn weights into usable throughput.
  5. 指标会从平均 tokens/s 转向 p99 TTFT、cache hit value、每任务成本和每瓦 tokens。 长上下文 Agent 的用户体验受尾延迟和重复 prefill 支配;数据中心侧的约束也从“有没有 GPU”扩展到“有没有电、有没有融资、有没有可持续利用率”。Metrics will move from average tokens/s to p99 TTFT, cache hit value, cost per task and tokens per watt. The user experience of long-context agents is governed by tail latency and repeated prefill; on the data-centre side the constraint has widened from "are there GPUs" to "is there power, financing and sustainable utilisation."
