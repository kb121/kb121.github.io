KV 池化与 KVConnectorKV Pooling & the KVConnector API

上一篇 Q / K / V 在 256K 对话窗口中的一生 算过一笔账:一个满窗口会攒下 80 GiB 的 KV cache。 这篇讲的是这 80 GiB 的归属权问题 —— 它默认属于某一个 vLLM 进程,进程之间看不见彼此,请求一结束就蒸发。 池化(pooling)就是把它从「实例私有的临时显存」改造成「可共享、可分层、可跨节点流动的资源」, 而 vLLM v1 里承接这件事的接口,就是 KVConnector。

一、为什么 KV 需要池化

默认状态下,KV cache 有三个「反资源化」的性质,每一个都在浪费算力:

  • 私有 —— 实例 A 算过的系统提示词 KV,实例 B 用不上,只能自己再算一遍。同一个 20K 的公司知识库前缀,10 个副本就要算 10 次。
  • 易失 —— 请求结束、或被抢占(preempt)时块被回收,下一轮对话回来,历史前缀得从头 prefill。
  • 同构 —— prefill 是算力密集的大 GEMM,decode 是访存密集的 GEMV。两者挤在同一张卡上,prefill 的长尾会直接拉高 decode 的 ITL。

池化解决的不是「KV 太大」,而是「同一份 KV 被算了很多遍、又很快被丢掉」。容量问题靠 GQA 和量化,重复问题只能靠共享。

二、KVConnector:调度器与 Worker 的分工

vLLM 没有把池化写死成某一种存储,而是抽了一个接口 KVConnectorBase_V1, 让 LMCache、Mooncake、NIXL 这些后端各自去实现。这个接口最关键的设计是按进程切成两侧:

这个切分的意义在于:调度器只需要知道「能省多少」这个数字就能排程,不必等数据真的到位。 所以 get_num_new_matched_tokens 被要求是无副作用的 —— 它可能被同一个请求反复调用, 而且允许返回 None 表示「还没查完,下个调度周期再问我」。

request_finished() 的返回值常被忽略,但它决定了块由谁释放: 若连接器接管异步发送(比如 PD 里 prefill 端还在往外推数据),调度器就不能立刻回收这些块,否则会把正在传输的数据覆盖掉。

四、池化的三种形态

同一个接口下,「池」可以是三种完全不同的东西。它们解决的问题不一样,也可以用 MultiConnector 叠在一起用(典型组合:PD 传输走 NIXL,同时各自向本地 LMCache 卸载)。

五、两处决定成败的工程细节

池化听起来只是「把数据搬走再搬回来」,但它能不能用,取决于两件很具体的事。

其一,搬运必须是异步的。 连接器 API 最早是同步的:vLLM 在读写外部 KV 时整个引擎是阻塞的, 省下的 prefill 时间还不够赔上等待时间。0.9.0 起 API 扩展为支持异步加载与保存,搬运才真正能和前向计算重叠 —— 这也是为什么接口里 start_load_kv 和 wait_for_layer_load 是分开的两个方法。

其二,显存布局决定了 DMA 效率。 这一点最不直观:KV 在显存里怎么摆,对模型计算的性能几乎没有影响, 但对卸载是致命的。原本每层的 K、V 各自成块,一次搬运被切成 2 × num_layers 个小片,DMA 全耗在发起开销上。 改成「一个连续物理块装下所有层」之后,有效块大小放大了 2 × num_layers 倍, 卸载吞吐提升了一个数量级。

六、配置速查与选型

三种形态都通过同一个启动参数 --kv-transfer-config 打开,区别只在 kv_connector 和 kv_role: 

# ① 分层卸载:把溢出的 KV 异步卸到 CPU 内存
vllm serve MODEL --kv-transfer-config '{
  "kv_connector": "OffloadingConnector",
  "kv_role": "kv_both",
  "kv_connector_extra_config": {"num_cpu_blocks": 100000}
}'

# ② PD 分离:prefill 端产,decode 端消,走 NIXL
vllm serve MODEL --kv-transfer-config '{
  "kv_connector": "NixlConnector",
  "kv_role": "kv_producer",
  "kv_load_failure_policy": "fail"
}'
# decode 实例同上,仅 kv_role 改成 "kv_consumer"

# ③ 组合:PD 传输走 NIXL,同时各自向共享池卸载
#    kv_connector 设为 "MultiConnector",
#    子连接器列在 kv_connector_extra_config.connectors 里

两个容易踩的参数:kv_role 有 kv_producer / kv_consumer / kv_both 三种, 分层卸载要用 kv_both(既存又取),PD 才是一产一消。 kv_load_failure_policy 默认是 fail —— 传输失败直接报错,而不是 recompute 悄悄回退去重算,因为在 decode 实例上临时插一段 prefill 会打乱低延迟调度、造成抖动。

你的瓶颈选哪种主要收益主要代价
显存不够,前缀反复被挤掉① 分层卸载扩大有效缓存容量,命中即省 prefillPCIe 带宽,冷数据回取有延迟
TTFT 与 ITL 互相拖累② PD 分离两阶段独立扩缩容,decode 尾延迟稳需要 RDMA 网络,运维复杂度上一个台阶

七、六个要点

01
池化治的是重复,不是容量

KV 太大靠 GQA、量化、稀疏来压;而同一份 KV 被反复计算又被丢弃,只能靠共享和持久化解决。这是两类正交的优化,别混为一谈。

02
接口按进程切,而不是按功能切

Scheduler 侧只做决策与记账、不碰张量,Worker 侧只管搬运。这让调度器拿到「能省多少 token」这个数字就能排程,不必等数据落地。

03
查询必须无副作用

get_num_new_matched_tokens 会被同一请求反复调用,实现里不能改状态。它还能返回 None 表示「查询未完成」,让调度器下轮再问 —— 这是远端查询不阻塞调度的关键。

04
逐层流水是延迟能被吃掉的原因

加载和保存都以层为粒度:wait_for_layer_load(i) 只挡住第 i 层。前面的层在算,后面的层在传,搬运时间被计算掩盖掉。

05
布局比算法更能决定吞吐

把 KV 改成「全层一个连续块」,有效块放大 2 × num_layers 倍,卸载吞吐提升一个数量级。对计算无感的排布方式,对 DMA 是生死线。

06
谁释放块,是正确性问题

request_finished() 要回答「现在能不能回收这些块」。连接器若还在异步外推,块就得由它接管释放,否则正在传输的数据会被下一个请求覆盖。

API 方法名与语义以 vLLM v1 KVConnectorBase_V1 源码为准;分层卸载的 TieringManager / SecondaryTierManager 属设计阶段接口, 落地范围以上游合入为准。容量与带宽为量级示意,非实测。
