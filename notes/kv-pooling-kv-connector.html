KV 池化与 KVConnectorKV Pooling & the KVConnector API

上一篇 Q / K / V 在 256K 对话窗口中的一生 算过一笔账:一个满窗口会攒下 80 GiB 的 KV cache。 这篇讲的是这 80 GiB 的归属权问题 —— 它默认属于某一个 vLLM 进程,进程之间看不见彼此,请求一结束就蒸发。 池化(pooling)就是把它从「实例私有的临时显存」改造成「可共享、可分层、可跨节点流动的资源」, 而 vLLM v1 里承接这件事的接口,就是 KVConnector。An earlier note, The life of Q / K / V in a 256K window, worked out that a full window accumulates 80 GiB of KV cache. This one is about who owns those 80 GiB — by default they belong to one vLLM process, invisible to any other, and they evaporate when the request ends. Pooling turns that from "temporary memory private to an instance" into "a shareable, tierable resource that can move across nodes", and the interface carrying it in vLLM v1 is the KVConnector.

一、为什么 KV 需要池化1 · Why KV needs pooling

默认状态下,KV cache 有三个「反资源化」的性质,每一个都在浪费算力:By default KV cache has three properties that keep it from behaving like a resource, each of them wasting compute:

  • 私有 —— 实例 A 算过的系统提示词 KV,实例 B 用不上,只能自己再算一遍。同一个 20K 的公司知识库前缀,10 个副本就要算 10 次。Private — the system-prompt KV that instance A computed is unusable by instance B, which has to recompute it. The same 20K company knowledge-base prefix gets computed 10 times across 10 replicas.
  • 易失 —— 请求结束、或被抢占(preempt)时块被回收,下一轮对话回来,历史前缀得从头 prefill。Volatile — blocks are reclaimed when the request ends or is preempted, so the next turn of a conversation has to prefill the history from scratch.
  • 同构 —— prefill 是算力密集的大 GEMM,decode 是访存密集的 GEMV。两者挤在同一张卡上,prefill 的长尾会直接拉高 decode 的 ITL。Homogeneous — prefill is a compute-bound large GEMM, decode a memory-bound GEMV. Squeeze both onto one GPU and prefill's long tail drives up decode's ITL directly.

池化解决的不是「KV 太大」,而是「同一份 KV 被算了很多遍、又很快被丢掉」。容量问题靠 GQA 和量化,重复问题只能靠共享。What pooling solves is not "KV is too large" but "the same KV is computed many times and then thrown away". Capacity is a job for GQA and quantisation; duplication can only be solved by sharing.

二、KVConnector:调度器与 Worker 的分工2 · KVConnector: the split between scheduler and worker

vLLM 没有把池化写死成某一种存储,而是抽了一个接口 KVConnectorBase_V1, 让 LMCache、Mooncake、NIXL 这些后端各自去实现。这个接口最关键的设计是按进程切成两侧:Rather than hard-coding one storage backend, vLLM abstracts an interface, KVConnectorBase_V1, and lets LMCache, Mooncake, NIXL and others implement it. Its most important design decision is to split along process boundaries:

这个切分的意义在于:调度器只需要知道「能省多少」这个数字就能排程,不必等数据真的到位。 所以 get_num_new_matched_tokens 被要求是无副作用的 —— 它可能被同一个请求反复调用, 而且允许返回 None 表示「还没查完,下个调度周期再问我」。The point of this split: the scheduler only needs the number "how much can be saved" in order to schedule, without waiting for the data to arrive. That is why get_num_new_matched_tokens is required to be side-effect free — it may be called repeatedly for the same request — and why it may return None to mean "the lookup has not finished; ask me again next scheduling cycle".

最小契约:40 个成员里只有 7 个必须实现The minimal contract: only 7 of 40 members are mandatory

把基类的方法按装饰器数一遍,KVConnectorBase_V1 一共 40 个成员,其中带 @abstractmethod 的只有 7 个 —— Worker 侧 4 个、Scheduler 侧 3 个,其余 33 个都给了默认实现。这 7 个就是接口的全部硬性要求:Counting the base class's methods by decorator, KVConnectorBase_V1 has 40 members, of which only 7 carry @abstractmethod — 4 on the worker side and 3 on the scheduler side. The other 33 ship with defaults. Those 7 are the entire hard requirement:

class KVConnectorBase_V1(ABC):
    # ========== Worker 侧:4 个 ==========
    @abstractmethod
    def start_load_kv(self, forward_context, **kwargs) -> None: ...

    @abstractmethod
    def wait_for_layer_load(self, layer_name: str) -> None: ...

    @abstractmethod
    def save_kv_layer(
        self, layer_name, kv_layer, attn_metadata, **kwargs,
    ) -> None: ...

    @abstractmethod
    def wait_for_save(self): ...

    # ========== Scheduler 侧:3 个 ==========
    @abstractmethod
    def get_num_new_matched_tokens(
        self, request: "Request", num_computed_tokens: int,
    ) -> tuple[int | None, bool]:
        """外部还能再给多少 token。None = 没查完,下轮再问;
        第二个返回值 = 是否异步加载(首个元素为 0 时必须是 False)。"""

    @abstractmethod
    def update_state_after_alloc(
        self, request: "Request", blocks: "KVCacheBlocks",
        num_external_tokens: int,
    ):
        """块分配完成后的回调。注意:要按 num_external_tokens 判断是否加载,
        而不是按 blocks 是否为空 —— MultiConnector 里没被选中的子连接器
        同样会收到真实的 blocks。"""

    @abstractmethod
    def build_connector_meta(self, scheduler_output) -> KVConnectorMetadata:
        """打包这一步要发给 Worker 的元数据。不得修改 scheduler_output,
        且调用本身会重置连接器状态。"""class KVConnectorBase_V1(ABC):

    @abstractmethod
    def start_load_kv(self, forward_context, **kwargs) -> None: ...

    @abstractmethod
    def wait_for_layer_load(self, layer_name: str) -> None: ...

    @abstractmethod
    def save_kv_layer(
        self, layer_name, kv_layer, attn_metadata, **kwargs,
    ) -> None: ...

    @abstractmethod

    # ========== Scheduler side: 3 ==========
    @abstractmethod
    def get_num_new_matched_tokens(
        self, request: "Request", num_computed_tokens: int,
    ) -> tuple[int | None, bool]:
        """How many more tokens the outside can supply. None = lookup
        unfinished, ask again next round; the second value = whether the
        load is async (must be False when the first element is 0)."""

    @abstractmethod
    def update_state_after_alloc(
        self, request: "Request", blocks: "KVCacheBlocks",
        num_external_tokens: int,
    ):
        """Called once blocks are allocated. Decide whether to load from
        num_external_tokens, not from whether blocks is empty — a non-chosen
        sub-connector of MultiConnector still gets the request's real blocks."""

    @abstractmethod
    def build_connector_meta(self, scheduler_output) -> KVConnectorMetadata:
        """Pack the metadata to ship to the workers this step. Must not modify
        scheduler_output, and calling it resets the connector's state."""

对照上面那张表会发现一个出入:request_finished 在表里被列为 Scheduler 侧的代表方法,但它不是抽象方法 —— 基类给了默认实现 return False, None,意思是「块可以立刻回收,没有额外传输参数」。 纯读取型的连接器不用管它;只要你的连接器在请求结束后还要往外推数据,就必须覆盖它,否则块会被提前回收。One discrepancy with the table above: request_finished is listed there as a representative scheduler-side method, but it is not abstract — the base class supplies return False, None, meaning "the blocks can be reclaimed right away, no extra transfer params". A read-only connector can ignore it; any connector that still pushes data out after a request ends must override it, or its blocks get reclaimed too early.

同一个类,实例化两次One class, instantiated twice

「按进程切两侧」在代码里不是两个基类,而是同一个类构造两次、靠 role 参数区分。 OffloadingConnector 的写法是这个模式最干净的样本:构造函数按 role 只建其中一半, 每个方法进来先 assert 自己确实在对应的那一侧。这个 assert 不是防御性代码,它就是接口契约本身 —— 在 Worker 进程里调 get_num_new_matched_tokens 会直接炸,而不是悄悄返回一个错的数字。"Split along process boundaries" is not two base classes in the code; it is one class constructed twice, distinguished by the role argument. OffloadingConnector is the cleanest sample of the pattern: the constructor builds only one half depending on role, and every method opens by asserting it really is on the matching side. That assert is not defensive padding, it is the contract itself — calling get_num_new_matched_tokens inside a worker process blows up rather than quietly returning a wrong number.

    SCHEDULER = 0   # 跑在调度器进程
    WORKER    = 1   # 跑在每个 worker 进程

    def __init__(self, vllm_config, role: KVConnectorRole, kv_cache_config):
        super().__init__(vllm_config, role, kv_cache_config)
        spec = OffloadingSpecFactory.create_spec(
            build_offloading_config(vllm_config, kv_cache_config))

        # 两侧的实现是两个独立对象,按 role 只建一个

        self.connector_worker: OffloadingConnectorWorker | None = None

            self.connector_scheduler = OffloadingConnectorScheduler(...)
        elif role == KVConnectorRole.WORKER:
            self.connector_worker = OffloadingConnectorWorker(...)

request_finished() 的返回值常被忽略,但它决定了块由谁释放: 若连接器接管异步发送(比如 PD 里 prefill 端还在往外推数据),调度器就不能立刻回收这些块,否则会把正在传输的数据覆盖掉。request_finished()'s return value is often overlooked, yet it determines who frees the blocks: if the connector takes over an asynchronous send (say the prefill side of a PD setup is still pushing data out), the scheduler must not reclaim those blocks immediately or it will overwrite data still in flight.

五、三处决定成败的工程细节5 · Three engineering details that decide whether it works


          
池化听起来只是「把数据搬走再搬回来」,但它能不能用,取决于三件很具体的事。前两件是它自己的性能问题,第三件是它向整个引擎收的税。Pooling sounds like just moving data out and back, but whether it is usable comes down to three very concrete things. The first two are its own performance problems; the third is a tax it levies on the rest of the engine.


          
其一,搬运必须是异步的。 连接器 API 最早是同步的:vLLM 在读写外部 KV 时整个引擎是阻塞的,
            省下的 prefill 时间还不够赔上等待时间。0.9.0 起 API 扩展为支持异步加载与保存,搬运才真正能和前向计算重叠 —— 
            这也是为什么接口里 start_load_kv 和 wait_for_layer_load 是分开的两个方法。First, the movement has to be asynchronous. The connector API started out synchronous: the whole engine blocked while vLLM read or wrote external KV,
            and the prefill time saved did not cover the time spent waiting. From 0.9.0 the API was extended to support asynchronous load and save, which is what finally lets movement overlap the forward pass —
            and why the interface separates start_load_kv from wait_for_layer_load.


          
其二,显存布局决定了 DMA 效率。 这一点最不直观:KV 在显存里怎么摆,对模型计算的性能几乎没有影响,
            但对卸载是致命的。原本每层的 K、V 各自成块,一次搬运被切成 2 × num_layers 个小片,DMA 全耗在发起开销上。
            改成「一个连续物理块装下所有层」之后,有效块大小放大了 2 × num_layers 倍,
            卸载吞吐提升了一个数量级。Second, memory layout determines DMA efficiency. This is the least intuitive part: how KV is arranged in memory barely affects model computation,
            but it is fatal for offloading. With each layer's K and V as their own block, one transfer is chopped into 2 × num_layers fragments and DMA spends all its time on issue overhead.
            Pack all layers into one contiguous physical block and the effective block size grows 2 × num_layers×,
            raising offload throughput by an order of magnitude.

def _coalesce_runs(runs: list[CopyRun]) -> tuple[CopyRun, ...]:
    """把 run 内部以及相邻 run 之间物理连续的片段塌缩掉,
    以最小化拷贝操作数(例如单 rank 映射会变成一整页一次拷贝)。"""
    out: list[CopyRun] = []
    for run in runs:
        # ① run 内部:步长恰好等于片段大小 ⇒ 整个 run 是一段连续字节
        if (run.num_fragments > 1
                and run.local_stride == run.fragment_size
                and run.canonical_stride == run.fragment_size):
            size = run.fragment_size * run.num_fragments
            run = CopyRun(run.local_offset, run.canonical_offset,
                          size, 1, size, size)

        # ② run 之间:上一段的尾巴正好接着这一段的头 ⇒ 并成一段
        prev = out[-1] if out else None
        if (prev is not None and prev.num_fragments == 1 and run.num_fragments == 1
                and prev.local_offset + prev.fragment_size == run.local_offset
                and prev.canonical_offset + prev.fragment_size
                    == run.canonical_offset):
            size = prev.fragment_size + run.fragment_size
            out[-1] = CopyRun(prev.local_offset, prev.canonical_offset,
                              size, 1, size, size)
        else:
            out.append(run)

            simply do not execute on replay, which turns them into a data race: the replayed graph reads KV that has not arrived yet.

            so Python can run between graph pieces. The price is one extra CPU-side launch between layers, which raises per-step decode latency.

    replay 时会被跳过,从而造成数据竞争。PIECEWISE 模式允许 Python
    代码在图的分段之间执行,确保同步正确。"""
    return False

# ② LMCache:只有真的开了 layerwise 才要求降级

    @classmethod
    def requires_piecewise_for_cudagraph(cls, extra_config) -> bool:
        return extra_config.get("use_layerwise", False)

# ③ 引擎配置阶段:静默覆盖用户设置,只打一行 warning
if (self.kv_transfer_config is not None
        and self.kv_transfer_config.is_kv_transfer_instance
        and self.compilation_config.cudagraph_mode.has_full_cudagraphs()):

            self.kv_transfer_config.kv_connector_extra_config):

            "due to layerwise async operations that cannot be "
            "captured in CUDA graphs. Overriding cudagraph_mode from %s "

            self.compilation_config.cudagraph_mode.name)
        self.compilation_config.cudagraph_mode = CUDAGraphMode.PIECEWISE# (1) the hook the base class leaves

    to return True when those operations are enabled. These operations
    cannot be captured in CUDA graphs and will be skipped during replay,
    causing data races. PIECEWISE mode allows Python code to execute
    between graph pieces, ensuring proper synchronization."""
    return False

            省下的 prefill 时间要先赔掉 decode 每步多出来的启动开销,净收益才是真收益。
            反过来,像 OffloadingConnector 这样把 wait_for_layer_load / save_kv_layer 实现成
            pass、全部搬运挤在 start_load_kv 一处发起的连接器,就不触发降级 —— 这是一个真实存在的设计取舍,
            而不只是实现风格的差别。piecewise 与 full 两种模式的区别见
            CUDA Graph 详解 & vLLM 里的 CUDA Graph 与精度。So "let's just try a connector" is not a free experiment: if you were running full CUDA graphs, the prefill time that layerwise offloading saves
            first has to pay back the extra per-step launch overhead in decode before any of it is net gain.
            Conversely, a connector like OffloadingConnector — which implements wait_for_layer_load / save_kv_layer as
            pass and issues every transfer from the single start_load_kv call — never triggers the demotion. That is a real design trade-off,
            not just a difference in implementation style. For the difference between piecewise and full mode, see
            CUDA Graph explained & CUDA graphs in vLLM.

七、八个要点7 · Eight takeaways


          

            
01
池化治的是重复,不是容量Pooling treats duplication, not capacity

              
KV 太大靠 GQA、量化、稀疏来压;而同一份 KV 被反复计算又被丢弃,只能靠共享和持久化解决。这是两类正交的优化,别混为一谈。KV being too large is a job for GQA, quantisation and sparsity; the same KV being computed repeatedly and then discarded can only be solved by sharing and persistence. Two orthogonal optimisations — do not conflate them.

            
02
接口按进程切,而不是按功能切The interface splits by process, not by function

              
Scheduler 侧只做决策与记账、不碰张量,Worker 侧只管搬运。这让调度器拿到「能省多少 token」这个数字就能排程,不必等数据落地。The scheduler side only decides and keeps books, never touching tensors; the worker side only moves data. This lets the scheduler schedule from the single number "how many tokens can be saved" without waiting for data to land.

            
03
查询必须无副作用The lookup must be side-effect free

              
get_num_new_matched_tokens 会被同一请求反复调用,实现里不能改状态。它还能返回 None 表示「查询未完成」,让调度器下轮再问 —— 这是远端查询不阻塞调度的关键。get_num_new_matched_tokens gets called repeatedly for the same request, so the implementation cannot mutate state. It can also return None for "lookup incomplete", letting the scheduler ask again next round — which is how a remote lookup avoids blocking scheduling.

            
04
逐层流水是延迟能被吃掉的原因Per-layer pipelining is why the latency disappears

              
加载和保存都以层为粒度:wait_for_layer_load(i) 只挡住第 i 层。前面的层在算,后面的层在传,搬运时间被计算掩盖掉。Load and save are both per layer: wait_for_layer_load(i) blocks only layer i. Earlier layers compute while later ones transfer, and the movement hides behind the computation.

            
05
布局比算法更能决定吞吐Layout decides throughput more than algorithms do

              
把 KV 改成「全层一个连续块」,有效块放大 2 × num_layers 倍,卸载吞吐提升一个数量级。对计算无感的排布方式,对 DMA 是生死线。Rearranging KV into one contiguous block per all layers grows the effective block 2 × num_layers× and lifts offload throughput by an order of magnitude. An arrangement the computation cannot feel is a life-or-death matter for DMA.

            
06
谁释放块,是正确性问题Who frees the blocks is a correctness question

              
request_finished() 要回答「现在能不能回收这些块」。连接器若还在异步外推,块就得由它接管释放,否则正在传输的数据会被下一个请求覆盖。request_finished() has to answer "can these blocks be reclaimed now". If the connector is still pushing asynchronously, it must take over freeing them, or the next request will overwrite data still in flight.

            
07
逐层回调要向 CUDA Graph 交税Per-layer callbacks pay a CUDA-graph tax

              
wait_for_layer_load / save_kv_layer 是 Python 代码,捕不进图。vLLM 的做法是把 cudagraph_mode 从 FULL 静默降到 PIECEWISE,只留一行 warning。省下的 prefill 要先赔掉 decode 每步多出的启动开销。wait_for_layer_load / save_kv_layer are Python and cannot be captured. vLLM's answer is to silently demote cudagraph_mode from FULL to PIECEWISE, leaving only a warning line. The prefill you save first has to pay back the extra per-step launch cost in decode.

            
08
异步加载期间,请求占块不产出During an async load a request holds blocks and produces nothing

              
连接器说要异步加载,调度器就把 num_new_tokens 设为 0、请求挂进 WAITING_FOR_REMOTE_KVS。显存已经分出去了,token 一个没产。池化的账不能只看命中率,还得算上这段空转占用。When the connector asks for an async load, the scheduler sets num_new_tokens to 0 and parks the request in WAITING_FOR_REMOTE_KVS. The memory is already committed and not one token comes out. The ledger for pooling is not just hit rate; it has to include this idle occupancy.
