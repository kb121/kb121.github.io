vLLM 的 gpu-memory-utilization 到底管什么(基于 v0.24)What gpu-memory-utilization Actually Controls in vLLM (v0.24)

这篇笔记基于 vLLM releases/v0.24.0 源码,图文讲清三件事:① gpu-memory-utilization 到底是什么;② 这笔"显存预算"是给谁的;③ 运行时是怎么一步步用它算出 KV cache 大小的。文中公式与结论都对应到具体源码位置。This note is based on the vLLM releases/v0.24.0 source and works through three things: ① what gpu-memory-utilization actually is, ② who that "memory budget" is for, and ③ how it turns into a KV cache size — plus a stage-by-stage table on whether to raise or lower it when you hit OOM.

一句话总览: gpu-memory-utilization(v0.24 默认 0.92)= 整卡总显存 × 比例 得到的一笔单实例显存预算。这笔预算要覆盖 模型权重 + 激活峰值 + 非-torch buffer(NCCL 等) + CUDA Graph,剩下的余额才是 KV cache。分母是总显存而不是"空闲显存"。In one line: gpu-memory-utilization (default 0.92 in v0.24) = total GPU memory × ratio, giving a per-instance memory budget. That budget has to cover weights, activations and CUDA Graph first; KV cache gets whatever is left.

0 · 三个最常见的误解0 · Three common misconceptions

❌ 常见误解❌ Common misconceptions

  • "它是拿空闲显存的百分比" —— 错,分母是整卡总显存。"It is a percentage of free memory" — no, the denominator is total GPU memory.
  • "这块显存全给 KV cache" —— 错,权重/激活/CUDA Graph 都从里面扣。"That memory all goes to KV cache" — no, weights, activations and CUDA Graph come out of it first.
  • "两个实例共卡,vLLM 会自己协调" —— 错,它是per-instance 上限,各设各的。"Two instances share a GPU, vLLM will coordinate" — no, it is a per-instance cap; each sets its own.

✅ 正确理解✅ The correct picture

  • 预算 = total_memory × util,一个绝对字节数。Budget = total_memory × util, an absolute byte count.
  • KV cache = 预算 − 其它所有开销后的余额。KV cache = the remainder after every other cost is deducted.
  • 调大 util ≈ 把余额几乎全喂给 KV cache(并发/上下文更大,但更易 OOM)。Raising util ≈ handing almost all of the remainder to KV cache — more concurrency and context, but closer to OOM.

1 · 它是什么:一笔"按比例"的显存预算1 · What it is: a proportional memory budget

参数定义在 vllm/config/cache.py 的 CacheConfig 里,取值范围 (0, 1],v0.24 默认 0.92(很多人记得的 0.9 在这个版本已经变成 0.92):The parameter lives in CacheConfig in vllm/config/cache.py, takes values in (0, 1], and defaults to 0.92 in v0.24 (the 0.9 many people remember became 0.92 in this release):

# vllm/config/cache.py
gpu_memory_utilization: float = Field(default=0.92, gt=0, le=1)
"""The fraction of GPU memory to be used for the model executor ...
This is a per-instance limit, and only applies to the current vLLM
instance. ... if you have two vLLM instances running on the same GPU,
you can set the GPU memory utilization to 0.5 for each instance."""

Worker 初始化时,把这个比例乘上整卡总显存,得到一笔以字节为单位的预算 requested_memory:At worker init this ratio is multiplied by total GPU memory to give a byte-denominated budget, requested_memory:

# vllm/v1/worker/utils.py — request_memory()
requested_memory = math.ceil(
    init_snapshot.total_memory * cache_config.gpu_memory_utilization
)
# 启动即校验:当前空闲显存不够这笔预算就直接报错
if init_snapshot.free_memory < requested_memory:
    raise ValueError("... Decrease GPU memory utilization ...")# vllm/v1/worker/utils.py — request_memory()
requested_memory = math.ceil(
    init_snapshot.total_memory * cache_config.gpu_memory_utilization
)
# Checked at startup: error out if free memory can't cover the budget
if init_snapshot.free_memory < requested_memory:
    raise ValueError("... Decrease GPU memory utilization ...")
为什么分母是"总显存"而不是"空闲显存"? 因为 vLLM 要给一个确定的、可预测的上限;总显存是常量,而空闲量随其它进程波动。留白的 1 − util 就是给驱动 context、其它进程、以及测量误差的安全垫。Why is the denominator total memory rather than free memory? Because vLLM wants a definite, predictable cap. Total memory is a constant; free memory fluctuates with other processes. The headroom is there so a single instance never claims the entire card.

2 · 预算给谁:一张图看懂内部拆解2 · Who the budget is for: one figure for the breakdown

这笔预算不是全给 KV cache。它要先养活整个实例的固定开销,剩下的才轮到 KV cache。vLLM 把非-KV-cache 的开销分成三类(见 memory_profiling 注释):权重、激活峰值、以及非-torch 部分(NCCL、部分 attention backend 的 buffer)。再加上 CUDA Graph 捕获的显存:The budget does not all go to KV cache. It first has to sustain the instance's fixed costs, and only then does KV cache get a turn. vLLM splits the non-KV-cache costs into three categories (see the memory_profiling comments): weights, activation peak and non-torch allocations.

Worker 用一次 dummy 前向做 profiling,测出前三项相加为 non_kv_cache_memory,然后从预算里减掉它和 CUDA Graph 的估算,得到 KV cache 可用显存:The worker runs one dummy forward pass to profile, sums the first three into non_kv_cache_memory, then subtracts that and the CUDA Graph estimate from the budget to get the memory available for KV cache:

# vllm/v1/worker/gpu_worker.py — determine_available_memory()
profile_result.non_kv_cache_memory = (
    profile_result.non_torch_increase      # 非-torch(NCCL 等)
    + profile_result.torch_peak_increase   # 激活峰值
    + profile_result.weights_memory        # 模型权重
)

self.available_kv_cache_memory_bytes = (
    self.requested_memory                  # 预算 = total × util
    - profile_result.non_kv_cache_memory   # 减去固定开销
    - cudagraph_memory_estimate_applied    # 减去 CUDA Graph
)# vllm/v1/worker/gpu_worker.py — determine_available_memory()
profile_result.non_kv_cache_memory = (
    profile_result.non_torch_increase      # non-torch (NCCL etc.)
    + profile_result.torch_peak_increase   # activation peak
    + profile_result.weights_memory        # model weights
)

self.available_kv_cache_memory_bytes = (
    self.requested_memory                  # budget = total × util
    - profile_result.non_kv_cache_memory   # minus fixed costs
    - cudagraph_memory_estimate_applied    # minus CUDA Graph
)
KV_cache 可用 = total_memory × util − ( weights + activation_peak + non_torch ) − cuda_graph = available_kv_cache_memory_bytesKV_cache available = total_memory × util − ( weights + activation_peak + non_torch ) − cuda_graph = available_kv_cache_memory_bytes

3 · 怎么用的:从比例到 KV block 的四步3 · How it is used: four steps from ratio to KV blocks

从一个 0~1 的比例,到最终"能放多少个 KV block、支持多大并发",中间是这样一条流水线:Getting from a 0~1 ratio to "how many KV blocks fit, and how much concurrency that supports" runs through this pipeline:

STEP 1
算预算 & 校验Compute budget & check
total × util 得预算;空闲不足直接报错。total × util gives the budget; error out if free memory is short.
STEP 2
Profiling
跑一次假前向,测权重 / 激活峰值 / 非-torch。Run a dummy forward to measure weights / activation peak / non-torch.
STEP 3
扣减Deduct
预算 − 固定开销 − CUDA Graph = KV cache 余额。Budget − fixed costs − CUDA Graph = KV cache remainder.
STEP 4
换算 blockConvert to blocks
余额 ÷ page_size ÷ 层数 = GPU KV block 数。Remainder ÷ page_size ÷ layer count = number of GPU KV blocks.

最后一步在 kv_cache_utils.py,把可用字节数换成 block 数,直接决定最大并发与最长上下文:The last step lives in kv_cache_utils.py, turning available bytes into a block count that directly sets maximum concurrency and context length:

# vllm/v1/core/kv_cache_utils.py — get_num_blocks()
num_blocks = int(available_memory // page_size // num_layers)
num_blocks = max(num_blocks, 0)
# 若算出 <= 0,会提示 "Try increasing gpu_memory_utilization ..."# vllm/v1/core/kv_cache_utils.py — get_num_blocks()
num_blocks = int(available_memory // page_size // num_layers)

4 · 四个必须知道的行为(v0.24)4 · Four behaviours you have to know (v0.24)

① CUDA Graph 显存默认从预算里"预扣"(v0.21 起)。 这意味着同一个 util 数值,比老版本留给 KV cache 的更少。日志甚至会告诉你:当前 util 等效于关闭 CUDA Graph profiling 时的多少 util、想维持同样 KV cache 该调到多少。可用环境变量 VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0 关掉这个预扣。① CUDA Graph memory is reserved out of the budget by default (since v0.21). The same util value therefore leaves less for KV cache than it did on older versions. The log will even tell you what your current util is equivalent to with the reservation disabled.
② kv_cache_memory_bytes / --kv-cache-memory 会直接绕过 util。 一旦显式指定 KV cache 字节数,vLLM 跳过 profiling 分配逻辑、忽略 gpu_memory_utilization,给你精确控制。vLLM 还会在日志里帮你算好一个建议值,方便从"比例模式"切到"精确字节模式"。② kv_cache_memory_bytes / --kv-cache-memory bypasses util entirely. Once you name a KV cache byte count explicitly, vLLM skips the profiling-based allocation path and ignores gpu_memory_utilization.
③ 它是 per-instance 上限,不做全卡协调。 同卡跑两个实例就各设 0.5;vLLM 不会感知另一个实例占了多少。③ It is a per-instance cap with no GPU-wide coordination. Running two instances on one card means setting 0.5 on each; vLLM has no idea how much the other one took.
④ 它不影响编译图结构。 源码把 gpu_memory_utilization 明确列为"不影响 compiled graph 的运行期旋钮"(ignored_factors),所以调它不会让 torch.compile / CUDA Graph 的编译缓存失效。④ It does not affect the compiled graph. The source explicitly lists gpu_memory_utilization among the runtime knobs that do not affect the compiled graph (ignored_factors), so changing it will not invalidate the compilation cache.

5 · 起服务 → 发请求:不同阶段 OOM 怎么调 util5 · Startup → serving: which way to move util at each stage

这是最容易踩坑的地方:不是所有 OOM 都靠"降 util"解决,有的反而要"升 util",有的 util 根本帮不上忙。 关键要看 OOM 发生在「分配 KV cache 之前」还是「之后」。下面按启动到收请求的时间线把每个 OOM 点拆开。This is where people most often go wrong: not every OOM is fixed by lowering util — some call for raising it, and for some util is irrelevant. What matters is whether the OOM happens before or after KV cache is allocated.

一句话判断: 报错里叫你 increase gpu_memory_utilization → 升;报错叫你 decrease 或崩在"占满整卡" → 降;崩在"权重/激活本身太大" → util 帮不上,得动 batch / 并行 / 量化。The one-line test: if the error tells you to increase gpu_memory_utilization → raise it; if it says decrease, or it dies from filling the whole card → lower it; if it dies during profiling or graph capture → util is largely beside the point, shrink the batch instead.

* 为什么 profiling OOM 降 util 没用? util 只决定"预算这个上限数字",而 profile_run 真正分配的激活张量大小由 batch(max-num-batched-tokens / max-num-seqs) 决定,和 util 无关。物理显存放不下这批激活,降 util 只会把预算数字改小,张量该多大还多大。所以要动的是 batch,不是 util。* Why does lowering util not help a profiling OOM? util only sets the budget number; the activation tensors profile_run actually allocates are sized by batch (max-num-batched-tokens / max-num-seqs) and sequence length. Shrink those instead.
关于第 ⑥ 步:KV cache 用尽通常不会让服务崩。 vLLM V1 里 KV block 是启动时一次性预分配好的;并发请求把 block 抢光时,调度器会走抢占 / 重算 / 排队(吞吐下降、延迟升高),而不是抛 CUDA OOM。所以运行时真的抛 OOM,基本不是 KV 不够,而是激活 / 碎片 / 外部进程——这些要靠"降 util 留余量 + 降 batch"来救。On step ⑥: running out of KV cache usually does not crash the service. In vLLM V1 the KV blocks are pre-allocated once at startup; when concurrent requests exhaust them the scheduler preempts and requeues rather than raising OOM.
最反直觉的一对: 同样是启动 OOM,②④⑥ 要降 util(给物理显存留余量),而 ⑤ 要升 util(把余额做大好放下 KV cache)。区分点就是——OOM 到底发生在「分配 KV cache 之前」(降)还是抱怨「KV cache 放不下」(升)。The most counter-intuitive pair: both are startup OOMs, yet ②④⑥ want util lowered (leave physical headroom) while ⑤ wants it raised (grow the remainder so KV cache fits). Read the error message to tell them apart.

6 · 实操建议6 · Practical guidance

  • 想要更大并发 / 更长上下文 → 调大 util(如 0.95),前提是没有别的进程抢显存。Want more concurrency or longer context → raise util (say 0.95), provided nothing else is competing for the card.
  • 同卡多实例 / 要给别的服务留显存 → 调小 util,并按实例数分配。Multiple instances per card, or leaving room for other services → lower util and divide it by instance count.
  • 频繁踩线 OOM 或想要可复现的显存占用 → 改用 --kv-cache-memory 精确指定,直接照 vLLM 日志给的建议值填。Repeatedly grazing OOM, or you want reproducible memory use → switch to --kv-cache-memory and use the exact value vLLM suggests in its log.
  • 从旧版本升级发现 KV cache 变小了 → 多半是 CUDA Graph 预扣所致,按日志提示适当上调 util,或关掉预扣。KV cache shrank after an upgrade → most likely the CUDA Graph reservation; raise util as the log suggests, or turn the reservation off.
