vLLM 的 gpu-memory-utilization 到底管什么(基于 v0.24)What gpu-memory-utilization Actually Controls in vLLM (v0.24)

这篇笔记基于 vLLM releases/v0.24.0 源码,图文讲清三件事:① gpu-memory-utilization 到底是什么;② 这笔"显存预算"是给谁的;③ 运行时是怎么一步步用它算出 KV cache 大小的。文中公式与结论都对应到具体源码位置。

一句话总览: gpu-memory-utilization(v0.24 默认 0.92)= 整卡总显存 × 比例 得到的一笔单实例显存预算。这笔预算要覆盖 模型权重 + 激活峰值 + 非-torch buffer(NCCL 等) + CUDA Graph,剩下的余额才是 KV cache。分母是总显存而不是"空闲显存"。

0 · 三个最常见的误解

❌ 常见误解

  • "它是拿空闲显存的百分比" —— 错,分母是整卡总显存。
  • "这块显存全给 KV cache" —— 错,权重/激活/CUDA Graph 都从里面扣。
  • "两个实例共卡,vLLM 会自己协调" —— 错,它是per-instance 上限,各设各的。

✅ 正确理解

  • 预算 = total_memory × util,一个绝对字节数。
  • KV cache = 预算 − 其它所有开销后的余额。
  • 调大 util ≈ 把余额几乎全喂给 KV cache(并发/上下文更大,但更易 OOM)。

1 · 它是什么:一笔"按比例"的显存预算

参数定义在 vllm/config/cache.py 的 CacheConfig 里,取值范围 (0, 1],v0.24 默认 0.92(很多人记得的 0.9 在这个版本已经变成 0.92): 

# vllm/config/cache.py
gpu_memory_utilization: float = Field(default=0.92, gt=0, le=1)
"""The fraction of GPU memory to be used for the model executor ...
This is a per-instance limit, and only applies to the current vLLM
instance. ... if you have two vLLM instances running on the same GPU,
you can set the GPU memory utilization to 0.5 for each instance."""

Worker 初始化时,把这个比例乘上整卡总显存,得到一笔以字节为单位的预算 requested_memory:

# vllm/v1/worker/utils.py — request_memory()
requested_memory = math.ceil(
    init_snapshot.total_memory * cache_config.gpu_memory_utilization
)
# 启动即校验:当前空闲显存不够这笔预算就直接报错
if init_snapshot.free_memory < requested_memory:
    raise ValueError("... Decrease GPU memory utilization ...")
为什么分母是"总显存"而不是"空闲显存"? 因为 vLLM 要给一个确定的、可预测的上限;总显存是常量,而空闲量随其它进程波动。留白的 1 − util 就是给驱动 context、其它进程、以及测量误差的安全垫。

2 · 预算给谁:一张图看懂内部拆解

这笔预算不是全给 KV cache。它要先养活整个实例的固定开销,剩下的才轮到 KV cache。vLLM 把非-KV-cache 的开销分成三类(见 memory_profiling 注释):权重、激活峰值、以及非-torch 部分(NCCL、部分 attention backend 的 buffer)。再加上 CUDA Graph 捕获的显存:

Worker 用一次 dummy 前向做 profiling,测出前三项相加为 non_kv_cache_memory,然后从预算里减掉它和 CUDA Graph 的估算,得到 KV cache 可用显存:

# vllm/v1/worker/gpu_worker.py — determine_available_memory()
profile_result.non_kv_cache_memory = (
    profile_result.non_torch_increase      # 非-torch(NCCL 等)
    + profile_result.torch_peak_increase   # 激活峰值
    + profile_result.weights_memory        # 模型权重
)

self.available_kv_cache_memory_bytes = (
    self.requested_memory                  # 预算 = total × util
    - profile_result.non_kv_cache_memory   # 减去固定开销
    - cudagraph_memory_estimate_applied    # 减去 CUDA Graph
)
KV_cache 可用 = total_memory × util − ( weights + activation_peak + non_torch ) − cuda_graph = available_kv_cache_memory_bytes

3 · 怎么用的:从比例到 KV block 的四步

从一个 0~1 的比例,到最终"能放多少个 KV block、支持多大并发",中间是这样一条流水线:

STEP 1
算预算 & 校验
total × util 得预算;空闲不足直接报错。
STEP 2
Profiling
跑一次假前向,测权重 / 激活峰值 / 非-torch。
STEP 3
扣减
预算 − 固定开销 − CUDA Graph = KV cache 余额。
STEP 4
换算 block
余额 ÷ page_size ÷ 层数 = GPU KV block 数。

最后一步在 kv_cache_utils.py,把可用字节数换成 block 数,直接决定最大并发与最长上下文:

# vllm/v1/core/kv_cache_utils.py — get_num_blocks()
num_blocks = int(available_memory // page_size // num_layers)
num_blocks = max(num_blocks, 0)
# 若算出 <= 0,会提示 "Try increasing gpu_memory_utilization ..."

4 · 四个必须知道的行为(v0.24)

① CUDA Graph 显存默认从预算里"预扣"(v0.21 起)。 这意味着同一个 util 数值,比老版本留给 KV cache 的更少。日志甚至会告诉你:当前 util 等效于关闭 CUDA Graph profiling 时的多少 util、想维持同样 KV cache 该调到多少。可用环境变量 VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=0 关掉这个预扣。
② kv_cache_memory_bytes / --kv-cache-memory 会直接绕过 util。 一旦显式指定 KV cache 字节数,vLLM 跳过 profiling 分配逻辑、忽略 gpu_memory_utilization,给你精确控制。vLLM 还会在日志里帮你算好一个建议值,方便从"比例模式"切到"精确字节模式"。
③ 它是 per-instance 上限,不做全卡协调。 同卡跑两个实例就各设 0.5;vLLM 不会感知另一个实例占了多少。
④ 它不影响编译图结构。 源码把 gpu_memory_utilization 明确列为"不影响 compiled graph 的运行期旋钮"(ignored_factors),所以调它不会让 torch.compile / CUDA Graph 的编译缓存失效。

5 · 起服务 → 发请求:不同阶段 OOM 怎么调 util

这是最容易踩坑的地方:不是所有 OOM 都靠"降 util"解决,有的反而要"升 util",有的 util 根本帮不上忙。 关键要看 OOM 发生在「分配 KV cache 之前」还是「之后」。下面按启动到收请求的时间线把每个 OOM 点拆开。

一句话判断: 报错里叫你 increase gpu_memory_utilization → 升;报错叫你 decrease 或崩在"占满整卡" → 降;崩在"权重/激活本身太大" → util 帮不上,得动 batch / 并行 / 量化。
阶段典型报错 / 现象根因util 怎么调更有效的手段
① 加载权重 CUDA out of memory(还没跑 profiling 就崩) 模型权重本身就放不下 ⚠️ 无用 加大 TP/PP、量化(fp8/awq/gptq)、cpu_offload_gb、换小模型
② 校验预算 "Free memory … is less than desired GPU memory utilization … Decrease GPU memory utilization" 空闲显存 < total×util(常是别的进程占了卡) ⬇️ 降 util 清理/隔离其它进程、独占容器
③ Profiling 前向 profile_run 时 CUDA OOM 激活峰值撑爆物理显存 ⚠️ 降 util 基本无用* 降 max-num-batched-tokens / max-num-seqs / max-model-len;开启 chunked prefill
④ CUDA Graph 捕获 capture 阶段 OOM graph 池 + 激活一起占满 ⬇️ 降 util 留余量 减少 capture 尺寸、--enforce-eager、关 full cudagraph
⑤ 分配 KV cache "No available memory for the cache blocks" / "estimated maximum model length is N … Try increasing gpu_memory_utilization" 扣完固定开销后余额太小,放不下 1 条 max_model_len ⬆️ 升 util 降 max-model-len;若被 CUDA Graph 预扣吃掉可关掉预扣
⑥ 收请求(运行时) 服务跑一段时间后 CUDA OOM 长 prompt / 大 prefill 激活超过 profiling 峰值、碎片、别的进程运行中抢显存 ⬇️ 降 util 留安全垫 降 max-num-batched-tokens、开 chunked prefill、隔离进程
* 为什么 profiling OOM 降 util 没用? util 只决定"预算这个上限数字",而 profile_run 真正分配的激活张量大小由 batch(max-num-batched-tokens / max-num-seqs) 决定,和 util 无关。物理显存放不下这批激活,降 util 只会把预算数字改小,张量该多大还多大。所以要动的是 batch,不是 util。
关于第 ⑥ 步:KV cache 用尽通常不会让服务崩。 vLLM V1 里 KV block 是启动时一次性预分配好的;并发请求把 block 抢光时,调度器会走抢占 / 重算 / 排队(吞吐下降、延迟升高),而不是抛 CUDA OOM。所以运行时真的抛 OOM,基本不是 KV 不够,而是激活 / 碎片 / 外部进程——这些要靠"降 util 留余量 + 降 batch"来救。
最反直觉的一对: 同样是启动 OOM,②④⑥ 要降 util(给物理显存留余量),而 ⑤ 要升 util(把余额做大好放下 KV cache)。区分点就是——OOM 到底发生在「分配 KV cache 之前」(降)还是抱怨「KV cache 放不下」(升)。

6 · 实操建议

  • 想要更大并发 / 更长上下文 → 调大 util(如 0.95),前提是没有别的进程抢显存。
  • 同卡多实例 / 要给别的服务留显存 → 调小 util,并按实例数分配。
  • 频繁踩线 OOM 或想要可复现的显存占用 → 改用 --kv-cache-memory 精确指定,直接照 vLLM 日志给的建议值填。
  • 从旧版本升级发现 KV cache 变小了 → 多半是 CUDA Graph 预扣所致,按日志提示适当上调 util,或关掉预扣。
速查公式
blocks = [ total_mem × util − (weights + act_peak + non_torch) − cuda_graph ] ÷ page_size ÷ num_layers
